Maestro

Every command

Written by the CLI itself when the book is built, so it says what this version of maestro takes. maestro <command> --help says the same in a terminal.

Every command also takes -h, --help, and these:

      --no-color        print without colours (as NO_COLOR=1 does)
      --server string   the Maestro server to talk to (default: the one kept, asked for the first time)

maestro build

Build a container image from a repo on one of your forges.

maestro build <repo> [flags]

Builds a container image from a repo's Dockerfile (or Containerfile) at the root of the repo, or from the one its maestro.toml names with dockerfile = "path/to/Dockerfile". The root of the repo is the build's context either way.

<repo> is a name, owner/name, or URL. The forge that has it is used; pass --forge when several do. A public repo on GitHub, GitLab or Codeberg needs no forge and no token: pass its full URL.

The build gets a number: maestro run <build> runs its image, and maestro builds shows the ones you have. With --run, the image is run as soon as it is built; --watch implies --run, and follows the run (not the build) until it is over.

To try a change without pushing it, send your own maestro.toml (-c), the generator it names (-g) or the Dockerfile (-f) from here: the server builds the repo with them in place of its own. Each may have any name here. A change to maestro.toml or the generator alone needs no new build: send them to maestro run instead, which runs the image you have.

Examples:

maestro build my-app
maestro build some-org/my-app --ref v1.2.0
maestro build https://github.com/some-org/public-app
maestro build my-app --watch
maestro build my-app -c bench.toml -g genvrs.py -f Dockerfile
build=$(maestro build my-app -q)

Flags:

  -c, --config string       a maestro.toml here to build with in place of the repo's
  -f, --dockerfile string   a Dockerfile here to build from in place of the repo's
      --forge string        which forge to use (see 'maestro forges list')
  -g, --generator string    a generator script here, in place of the one maestro.toml names
  -n, --interval duration   how often to refresh with --watch (at least 1s) (default 2s)
      --json                print the build (and its run, with --run) as JSON, and nothing else on stdout
  -q, --quiet               print only the number of the build (and its run, with --run), and nothing else on stdout
      --ref string          branch, tag or commit to build (default: the default branch)
      --run                 run the image once it is built
  -w, --watch               run the image once it is built (as --run), and follow the run until it is over

maestro builds

Commands for what maestro build built.

maestro builds [flags]

Also: image.

Flags:

      --json   print the builds as JSON

Commands:

  • maestro builds list: List your builds, and whether each still has its image
  • maestro builds rm: Remove the image a build produced
  • maestro builds run: Run a build's image on the machines (as maestro run)

maestro builds list

List your builds, and whether each still has its image.

maestro builds list [flags]

Lists every build of yours, newest first: the ones that worked, the ones that failed and why, and any still going. IMAGE is the size of the image a build has, or "removed" once it is gone; only a build with an image can be run. BUILD is the number maestro run and maestro builds rm take.

Flags:

      --json   print the builds as JSON

maestro builds rm

Remove the image a build produced.

maestro builds rm <build> [flags]

Removes the image of a build, from the server and from the machines. Each user may keep a limited number of images; this frees a place for a new build. The build's record and its runs, with their files, are kept.

<build> is the build number shown by maestro builds list, with or without #.

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro builds run

Run a build's image on the machines (as maestro run).

maestro builds run <build> [flags]

Queues a run of the image a build produced: one container per line of parameters in the repo's maestro.toml, and per line its generator yielded when the image was built, spread over the machines it names. Without a maestro.toml, a single container runs the image's own command.

<build> is the build number shown by maestro builds, with or without #. Containers start as machines have room; --watch follows them until the run is over, as maestro runs show <run> --watch does later, and exits 1 if the run failed.

To try other lines without a new build, send your own maestro.toml (-c) or the generator it names (-g) from here: the server reads them against the repo as the build had it and runs the build's image on the lines they make. Each may have any name here. A Dockerfile changes the image, which takes maestro build -f.

maestro help concepts says what lines are.

Examples:

maestro builds run 12 --watch
maestro builds run 12 -c small.toml --watch
maestro builds run 12 -g genvrs.py
run=$(maestro builds run 12 -q) && maestro runs show "$run" --watch

Flags:

  -c, --config string       a maestro.toml here to make the lines from in place of the build's
  -g, --generator string    a generator script here, in place of the one maestro.toml names
  -n, --interval duration   how often to refresh with --watch (at least 1s) (default 2s)
      --json                print the queued run as JSON, and nothing else on stdout
  -q, --quiet               print only the number of the queued run, and nothing else on stdout
  -w, --watch               follow the run until it is over; exit 1 if it failed

maestro completion bash

Generate the autocompletion script for bash.

maestro completion bash

Generate the autocompletion script for the bash shell.

This script depends on the 'bash-completion' package. If it is not installed already, you can install it via your OS's package manager.

maestro completion bash > /etc/bash_completion.d/maestro

maestro docs

Open the Maestro book, on a topic or a command.

maestro docs [topic | command…] [flags]

Opens the Maestro book in a browser, and prints its link: the book explains how Maestro builds, queues and runs your containers, and how to set it up.

Name a topic (maestro docs queue) to open its page, or a command (maestro docs runs logs) for what it takes.

maestro carries the book, so it opens offline, without signing in: it is served from this computer only (127.0.0.1), until ctrl-c, so that any browser opens it whole, a sandboxed one too. --web opens the copy your Maestro server serves instead, which can be opened on another machine, as when this one is reached over SSH. MAESTRO_DOCS_URL points at another copy still.

Also: doc.

Examples:

maestro docs
maestro docs toml
maestro docs runs logs
maestro docs queue --web --url

Flags:

      --url    only print the link, without opening a browser
      --web    the book your Maestro server serves, instead of the one maestro carries

maestro export

Write what happened to your lines over a period, as CSV.

maestro export [flags]

Writes a row for each line of the runs queued over a period: its run and line, whose it is, its cores and memory, the machine it ran on, its status, the scheduler settings it was assigned under, when it was submitted, assigned, started and finished, and the group its user was in when it was assigned. It is what sim evaluate, in maestro-orq, measures waits, slowdowns, utilization, fairness and the objective Z from, the same as for a simulation.

Administrators can export everyone's lines with --all.

Examples:

maestro export --since 2026-11-01 --until 2026-11-08 > lines.csv
maestro export --since 2026-11-01 --all -o lines.csv
maestro export --since 30d -o month.csv

Flags:

      --all             everyone's lines (administrators)
  -o, --output string   the file to write; the standard output when left out
      --since string    from this day (2026-11-01), RFC 3339 time or so long ago (12h, 7d, 2w) on; a week ago when left out
      --until string    until before this day, time or so long ago; now when left out

maestro forges

Manage the git forges Maestro reads repositories from.

maestro forges [flags]

A forge is where your repositories live: GitHub, Forgejo (Codeberg, Gitea) or GitLab. Maestro only reads from it.

Also: forge.

Flags:

      --json   print the forges as JSON

Commands:

  • maestro forges add: Add a forge and its token
  • maestro forges list: List the configured forges
  • maestro forges rm: Remove a forge and forget its token

maestro forges add

Add a forge and its token.

maestro forges add [name] [flags]

Adds a forge, or replaces the one with the same name. The token is checked before it is stored. Only Forgejo takes a --url.

The token is kept in the system keyring. Without --store-in-file, adding a forge goes back to the keyring; with it, secrets are kept in the config file.

Examples:

maestro forges add
maestro forges add --kind gitlab
maestro forges add work --kind forgejo --url https://git.example.com

Flags:

      --kind string     forge kind: github, forgejo, gitlab
      --store-in-file   keep secrets in the config file instead of the system keyring, for good
      --url string      Forgejo instance URL (default: https://codeberg.org)

maestro forges list

List the configured forges.

maestro forges list [flags]

Flags:

      --json   print the forges as JSON

maestro forges rm

Remove a forge and forget its token.

maestro forges rm <name> [flags]

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro keys

List and revoke your Maestro keys.

maestro keys [flags]

Lists the Maestro keys you have on the server, newest first. Each maestro login issues one, on whichever computer you run it. A key is shown by its prefix, the first 10 characters, and never in full. The one this computer uses is marked.

Examples:

maestro keys
maestro keys rm mk_Q3xv9aZ

Flags:

      --json   print the keys as JSON

Commands:

  • maestro keys rm: Revoke one of your Maestro keys

maestro keys rm

Revoke one of your Maestro keys.

maestro keys rm <prefix> [flags]

Revokes the key that starts with <prefix>, as maestro keys shows it. The key stops working at once, on every computer that holds it. It asks first.

Revoke a key this way when you no longer trust a computer you signed in on. To end the key of the computer you are on, maestro logout does it and forgets the key too.

Also: revoke.

Examples:

maestro keys rm mk_Q3xv9aZ

Flags:

  -y, --yes    don't ask first

maestro login

Sign the CLI in to Maestro.

maestro login [flags]

Prints a link to the Maestro page and a short code to approve there. The link can be opened in any browser, on this machine or another.

With --server, signs in to that Maestro server, which every command then talks to; without it, to the one kept, which is asked for the first time. The key is only ever sent to the server that minted it.

The key is kept in the system keyring, and a login without --store-in-file goes back to it. If yours asks for a password, or has none, pass --store-in-file to keep secrets in the config file (readable only by you) instead.

Flags:

      --store-in-file   keep secrets in the config file instead of the system keyring, for good

maestro logout

Revoke your Maestro key and forget everything the CLI has stored.

maestro logout [flags]

Revokes the Maestro key on the server that issued it, then forgets the key, the server and every forge with its token on your computer.

If the server can't be reached, it still forgets the key, and says that the key is still valid there. Revoke it later with maestro keys rm <prefix> from a computer that is signed in.

A forge token stays valid on its forge. Revoke it there if you no longer trust this computer.

Flags:

  -y, --yes    don't ask for confirmation

maestro machines list

List the machines, and whether Maestro can reach them now.

maestro machines list [flags]

Lists the machines an administrator added on the Maestro page. Their names are what maestro.toml refers to them by.

Flags:

maestro machines stats

Print how loaded the machines are, once.

maestro machines stats [machine] [flags]

Prints a table of every machine's CPU, memory, GPUs, load, the cores and memory lines take of what it has for them (with the lines waiting, as +N) and containers once. With --json, prints everything Maestro knows, for scripts.

For something to watch, use maestro top.

Flags:

      --json   print everything as JSON

maestro queue

Show where lines wait, and your share of the machines.

maestro queue [flags]

Shows how many lines wait and run, everyone's together and yours:

queued    in their user's queue
heads     how many of those are their user's head, in the dispatcher queue
assigned  given to a machine, waiting for room on it
starting, running

It also shows your share of the machines, as the scheduler weighs it when it chooses whose line goes next.

A user's head is the first of their queued lines. Users are in groups, and the heads of a group's users make its dispatcher queue. Groups take turns at the machines, and in a group's turn one of its heads goes to a machine. You see your group. Administrators see every user and every group, with the number an administrator weighs a user by.

It ends with how the scheduler is set up. maestro settings shows all of it.

Flags:

      --json   print the queue as JSON

Run the image of one of your builds on the machines.

maestro run <build> [flags]

Queues a run of the image a build produced: one container per line of parameters in the repo's maestro.toml, and per line its generator yielded when the image was built, spread over the machines it names. Without a maestro.toml, a single container runs the image's own command.

<build> is the build number shown by maestro builds, with or without #. Containers start as machines have room; --watch follows them until the run is over, as maestro runs show <run> --watch does later, and exits 1 if the run failed.

To try other lines without a new build, send your own maestro.toml (-c) or the generator it names (-g) from here: the server reads them against the repo as the build had it and runs the build's image on the lines they make. Each may have any name here. A Dockerfile changes the image, which takes maestro build -f.

maestro help concepts says what lines are.

Examples:

maestro run 12 --watch
maestro run 12 -c small.toml --watch

Flags:

  -c, --config string       a maestro.toml here to make the lines from in place of the build's

maestro runs

Commands for the runs started with maestro run.

maestro runs [flags]

maestro runs cancel

Cancel a run: drop what hasn't started and stop what has.

maestro runs cancel <run> [flags]

Flags:

maestro runs get

Download the files kept from a run.

maestro runs get <run> [dir] [flags]

Downloads every file kept from a run's containers into <dir>/<run>/<line>/, and what each printed among them, as stdout.log and stderr.log (dir defaults to the current directory). --line picks some lines only. A run already downloaded there is only downloaded over with --force.

Examples:

maestro runs get 31
maestro runs get 31 results/ --line 2 --line 5

Flags:

      --force             download over a run already downloaded there
      --line int64Slice   only this line (again for more) (default [])

maestro runs list

List your runs.

maestro runs list [flags]

Lists your runs, newest first: the last --limit of them (20; 0 for all), of a --status (queued, running, succeeded, failed, cancelled) or a --repo if asked. --json prints the same runs. With --watch, the list is drawn again every --interval until you press ctrl-c. With --all, an administrator is given everyone's runs, and whose each is.

Flags:

      --all                 everyone's runs (administrators only)
  -n, --interval duration   how often to refresh with --watch (at least 1s) (default 2s)
      --json                print the runs as JSON
      --limit int           how many runs, newest first; 0 for all (default 20)
      --repo string         only the runs of this repo (owner/name, or name)
      --status string       only the runs with this status
  -w, --watch               keep showing it, refreshed as it changes

maestro runs logs

Print what a line's container wrote to stdout and stderr.

maestro runs logs <run> [line] [flags]

Prints what a line's container wrote: its stdout to stdout and its stderr to stderr, so the two can be told apart or sent to different places. The line may be left out of a run that has only one.

With -f, a line that hasn't started yet is waited for, and what a running line prints is followed until it ends, as tail -f does.

Once a line is over, all of its stdout comes before all of its stderr; how they were mixed as the container ran isn't kept.

Examples:

maestro runs logs 31 2 -f
maestro runs logs 31 2 2>/dev/null   # only what it printed to stdout
maestro runs logs 31 2 >/dev/null    # only what it printed to stderr

Flags:

  -f, --follow     wait for the line to start, and follow what it prints until it ends
      --tail int   only the last N lines of a line still running (all when left out)

maestro runs rm

Delete a finished run and the files kept from it.

maestro runs rm <run> [flags]

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro runs show

Show each line of a run: where it ran, how it ended, what it kept.

maestro runs show [run] [flags]

Shows each line of a run: where it ran, how it ended, what it kept. With --watch, it is drawn again every --interval until the run is over, or you press ctrl-c, and exits 1 if the run failed. Without a run, it shows your newest. --failed shows only the lines that failed, errored or were cancelled.

Flags:

      --failed              only the lines that failed, errored or were cancelled
  -n, --interval duration   how often to refresh with --watch (at least 1s) (default 2s)
      --json                print the run as JSON
  -w, --watch               keep showing it, refreshed as it changes; exit 1 if the run failed

maestro settings

Show the server's settings: the image limit and how lines are scheduled.

maestro settings [flags]

Shows how many images each user may keep, and how the scheduler chooses whose line goes next and where: the policy of each of the three queues, the score's weights and how a user's share of the machines is measured. An administrator changes them on the Maestro page.

Flags:

      --json   print the settings as JSON

maestro top

Watch how loaded the machines are, like top.

maestro top [machine] [flags]

Shows every machine on a row: CPU, memory, GPUs, load, how many of the cores it has for lines they take and how many lines wait (6/14 +3), refreshed as you watch. Press enter on a machine for its cores, memory, disks, network, GPUs and the containers on it with whose they are, or name a machine to open it straight away.

Anyone signed in sees the machines and their own containers. Administrators also see every container, and the server Maestro runs on, as "orq".

Many people watching share one reading: Maestro takes it at most every couple of seconds, however many windows are open.

Flags:

  -n, --interval duration   how often to refresh (at least 1s) (default 2s)

maestro usage

Show how much your lines have used.

maestro usage [flags]

Shows the core-hours and memory GB-hours your lines used over the last days, counted as each line ends. What you used counts against you, less as it gets older, when the scheduler weighs whose line goes next, if an administrator set it up so.

Administrators see everyone's, or one user's with --user, by their number or email.

Examples:

maestro usage --daily --days 7
maestro usage --user ana@example.org

Flags:

      --daily         a row for each day
      --days int      how many days back (default 30)
      --json          print the usage as JSON, a day at a time
      --user string   one user's usage, by their number or email (administrators)
