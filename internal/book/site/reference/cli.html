Maestro

Every command

Written by the CLI itself when the book is built, so it says what this version of maestro takes. maestro <command> --help says the same in a terminal.

Every command also takes -h, --help, and these:

      --no-color     print without colours (as NO_COLOR=1 does)
      --server url   the url of the Maestro server to talk to (default: the server the CLI kept, which it asks for the first time)

maestro build

Build a container image from a repository on one of your forges.

maestro build <repo> [flags]

Builds a container image from the Dockerfile, or Containerfile, at the root of a repository. When the repository's maestro.toml names another one with dockerfile = "path/to/Dockerfile", it builds from that one. Either way, the build's context is the root of the repository.

<repo> is a name, owner/name or URL. The CLI uses the forge that has it, and when several of your forges have it, you pick one with --forge. A public repository on GitHub, GitLab or Codeberg needs no forge and no token: pass its full URL.

The build gets a number. maestro run <build> runs its image, and maestro builds shows the builds you have. With --run, it starts a run as soon as the image is built. --watch does the same, then follows the run, not the build, until the run is over.

To try a change without pushing it, send your own maestro.toml (-c), the generator it names (-g) or the Dockerfile (-f) from your computer. The server builds the repository with them in place of its own. Your files can have any name. A change to maestro.toml or the generator alone needs no new build: send the files to maestro run instead, which runs the image you have.

Examples:

maestro build my-app
maestro build some-org/my-app --ref v1.2.0
maestro build https://github.com/some-org/public-app
maestro build my-app --watch
maestro build my-app -c bench.toml -g genvrs.py -f Dockerfile
build=$(maestro build my-app -q)

Flags:

  -c, --config file         a file on your computer to build with as maestro.toml, in place of the repository's
  -f, --dockerfile file     a file on your computer to build from as the Dockerfile, in place of the repository's
      --forge name          the name of the forge to use, as maestro forges list shows it
  -g, --generator script    a generator script on your computer, in place of the one maestro.toml names
  -n, --interval duration   how often to redraw with --watch, at least 1s (default 2s)
      --json                print the build (and its run, with --run) as JSON, and nothing else on standard output
  -q, --quiet               print only the number of the build (and its run, with --run), and nothing else on standard output
      --ref ref             build this ref, a branch, tag or commit (default: the repository's default branch)
      --run                 start a run once the image is built
  -w, --watch               start a run once the image is built, as --run does, and follow it until it is over

maestro builds

List your builds and remove their images.

maestro builds [flags]

Also: image.

Flags:

      --json   print the builds as JSON

Commands:

  • maestro builds list: List your builds, and whether each still has its image
  • maestro builds rm: Remove the image a build made
  • maestro builds run: Run a build's image on the machines, as maestro run does

maestro builds list

List your builds, and whether each still has its image.

maestro builds list [flags]

Lists every build of yours, newest first: the ones that worked, the ones that failed and why, and the ones still building. IMAGE is the size of the build's image, or "removed" once the image is gone. Only a build with an image can be run. BUILD is the number maestro run and maestro builds rm take.

Flags:

      --json   print the builds as JSON

maestro builds rm

Remove the image a build made.

maestro builds rm <build> [flags]

Removes the image of a build, from the server and from the machines. You keep at most 10 images, unless your administrator set another number, and removing one frees a place for a new build. Maestro keeps the build's record and its runs, with their files. It asks first.

<build> is the build's number as maestro builds list shows it, with or without #.

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro builds run

Run a build's image on the machines, as maestro run does.

maestro builds run <build> [flags]

Queues a run of a build's image. The run starts one container for each line of parameters in the repository's maestro.toml, and one for each line its generator yielded when the image was built, on the machines maestro.toml names. Without a maestro.toml, one container runs the image's own command.

<build> is the build's number as maestro builds shows it, with or without #. Containers start as the machines have room. With --watch, it follows the run until the run is over, as maestro runs show <run> --watch does later, and exits with status 1 if the run failed.

To try other lines without a new build, send your own maestro.toml (-c) or the generator it names (-g) from your computer. The server reads them against the repository as the build had it, and runs the build's image on the lines they make. Your files can have any name. A Dockerfile changes the image, so it takes maestro build -f.

maestro help concepts says what lines are.

Examples:

maestro builds run 12 --watch
maestro builds run 12 -c small.toml --watch
maestro builds run 12 -g genvrs.py
run=$(maestro builds run 12 -q) && maestro runs show "$run" --watch

Flags:

  -c, --config file         a file on your computer to make the lines from as maestro.toml, in place of the build's
  -g, --generator script    a generator script on your computer, in place of the one maestro.toml names
  -n, --interval duration   how often to redraw with --watch, at least 1s (default 2s)
      --json                print the queued run as JSON, and nothing else on standard output
  -q, --quiet               print only the number of the queued run, and nothing else on standard output
  -w, --watch               follow the run until it is over, and exit with status 1 if it failed

maestro completion bash

Generate the autocompletion script for bash.

maestro completion bash

Generate the autocompletion script for the bash shell.

This script depends on the 'bash-completion' package. If it is not installed already, you can install it via your OS's package manager.

To load completions in your current shell session:

source <(maestro completion bash)

To load completions for every new session, execute once:

maestro completion bash > /etc/bash_completion.d/maestro

maestro completion bash > $(brew --prefix)/etc/bash_completion.d/maestro

You will need to start a new shell for this setup to take effect.

Flags:

      --no-descriptions   disable completion descriptions

maestro docs

Open the Maestro book, on a topic or a command.

maestro docs [topic | command…] [flags]

Opens the Maestro book in a browser, and prints its link. The book explains how Maestro builds, queues and runs your containers, and how to set it up.

Name a topic (maestro docs queue) to open its page, or a command (maestro docs runs logs) to see what it takes.

maestro carries the book, so it opens offline and without signing in. The CLI serves it from your computer only (127.0.0.1) until you press Ctrl-C, so any browser on your computer opens it whole, a sandboxed one too. Without a browser, as over SSH, it prints the link and serves the book all the same.

With MAESTRO_DOCS_URL set, it opens the copy of the book at that address instead, and serves nothing itself.

Also: doc.

Examples:

maestro docs
maestro docs toml
maestro docs runs logs
maestro docs queue --url

Flags:

      --url    only print the link, without opening a browser

maestro export

Write what happened to your lines over a period, as CSV.

maestro export [flags]

Writes a row for each line of the runs queued over a period: its run and line, whose it is, its cores and memory, the machine it ran on, its status, the scheduler settings it was assigned under, when it was submitted, assigned, started and finished, and the group its user was in when it was assigned. An administrator can measure it with orq's sim evaluate, as for a simulation: waits, slowdowns, utilization, fairness and the objective Z.

Administrators can export everyone's lines with --all.

Examples:

maestro export --since 2026-11-01 --until 2026-11-08 > lines.csv
maestro export --since 2026-11-01 --all -o lines.csv
maestro export --since 30d -o month.csv

Flags:

      --all           everyone's lines (administrators only)
  -o, --output file   the file to write (default: standard output)
      --since time    start at this time: a day (2026-11-01), an RFC 3339 time, or an age such as 12h, 7d or 2w (default: a week ago)
      --until time    end before this time, given the same ways (default: now)

maestro forges

Add, list and remove the git forges Maestro reads repositories from.

maestro forges [flags]

Lists the git forges the CLI keeps. A forge is where your repositories live: GitHub, GitLab, Codeberg, or another Forgejo or Gitea server. Maestro only reads from it.

Also: forge.

Flags:

      --json   print the forges as JSON

Commands:

  • maestro forges add: Add a forge and its token
  • maestro forges list: List your forges
  • maestro forges rm: Remove a forge and forget its token

maestro forges add

Add a forge and its token.

maestro forges add [name] [flags]

Adds a forge, or replaces the one with the same name. It checks the token before it keeps it. Only a Forgejo forge takes --url.

The CLI keeps the token in the system keyring. Without --store-in-file, adding a forge goes back to the keyring. With it, the CLI keeps secrets in the config file.

Examples:

maestro forges add
maestro forges add --kind gitlab
maestro forges add work --kind forgejo --url https://git.example.com

Flags:

      --kind kind       the kind of forge: github, forgejo, gitlab
      --store-in-file   keep secrets in the config file from now on, instead of the system keyring
      --url url         the Forgejo server's url (default: https://codeberg.org)

maestro forges list

List your forges.

maestro forges list [flags]

Flags:

      --json   print the forges as JSON

maestro forges rm

Remove a forge and forget its token.

maestro forges rm <name> [flags]

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro keys

List and revoke your Maestro keys.

maestro keys [flags]

Lists the Maestro keys you have on the server, newest first. Each maestro login issues one, on whichever computer you run it. A key is shown by its prefix, the first 10 characters, and never in full, with when it was created and when it expires. It marks the one this computer uses.

A key expires 90 days after it was issued, unless your administrator set another length. Run maestro login again for a new one.

Examples:

maestro keys
maestro keys rm mk_Q3xv9aZ

Flags:

      --json   print the keys as JSON

Commands:

  • maestro keys rm: Revoke one of your Maestro keys

maestro keys rm

Revoke one of your Maestro keys.

maestro keys rm <prefix> [flags]

Revokes the key that starts with <prefix>, as maestro keys shows it. The key stops working at once, on every computer that holds it. It asks first.

Revoke a key this way when you no longer trust a computer you signed in on. To end the key of the computer you are on, maestro logout does it and forgets the key too.

Also: revoke.

Examples:

maestro keys rm mk_Q3xv9aZ

Flags:

  -y, --yes    don't ask first

maestro login

Sign the CLI in to Maestro.

maestro login [flags]

Prints a link to the Maestro page and a short code for you to approve there. You can open the link in any browser, on your computer or another one.

With --server, it signs you in to that Maestro server, and every later command talks to it. Without --server, it uses the server the CLI has kept, and asks for one the first time. The CLI sends your key only to the server that issued it.

The CLI keeps your key in the system keyring. Without --store-in-file, maestro login goes back to the keyring. If your keyring asks for a password, or you have none, pass --store-in-file to keep secrets in the config file instead. Only you can read that file.

Flags:

      --store-in-file   keep secrets in the config file from now on, instead of the system keyring

maestro logout

Revoke your Maestro key and forget everything the CLI has stored.

maestro logout [flags]

Revokes the Maestro key on the server that issued it, then forgets the key, the server and every forge with its token on your computer.

If the server can't be reached, it still forgets the key, and says that the key is still valid there. Revoke it later with maestro keys rm <prefix> from a computer that is signed in.

A forge token stays valid on its forge. Revoke it there if you no longer trust this computer.

Flags:

  -y, --yes    don't ask first

maestro machines [flags]

Also: machine.

      --json   print the machines as JSON

Commands:

  • maestro machines list: List the machines, and whether Maestro can reach them now
  • maestro machines stats: Print how loaded the machines are, once

maestro machines list

List the machines, and whether Maestro can reach them now.

maestro machines list [flags]

Lists the machines an administrator added on the Maestro page. maestro.toml names a machine by the name this list shows.

Flags:

      --json   print the machines as JSON

maestro machines stats

Print how loaded the machines are, once.

maestro machines stats [machine] [flags]

Prints a table of every machine once: its CPU, memory, GPUs and load, the cores and memory lines take of what it has for them, with the lines waiting as +N, and its containers. With --json, it prints everything Maestro knows, for scripts.

To watch the machines, use maestro top.

Flags:

      --json   print everything as JSON

maestro queue

Show where lines wait, and your share of the machines.

maestro queue [flags]

Shows how many lines wait and run, everyone's together and yours:

queued    in their user's queue
heads     how many of those are their user's head, in the dispatcher queue
assigned  given to a machine, waiting for room on it
starting, running

It also shows your share of the machines, as the scheduler weighs it when it chooses whose line goes next.

A user's head is the first of their queued lines. Users are in groups, and the heads of a group's users make its dispatcher queue. Groups take turns at the machines, and in a group's turn one of its heads goes to a machine. You see your group. Administrators see every user and every group, with the number an administrator weighs a user by.

It ends with how the scheduler is set up. maestro settings shows all of it.

Flags:

      --json   print the queue as JSON

maestro run

Run the image of one of your builds on the machines.

maestro run <build> [flags]

Queues a run of a build's image. The run starts one container for each line of parameters in the repository's maestro.toml, and one for each line its generator yielded when the image was built, on the machines maestro.toml names. Without a maestro.toml, one container runs the image's own command.

<build> is the build's number as maestro builds shows it, with or without #. Containers start as the machines have room. With --watch, it follows the run until the run is over, as maestro runs show <run> --watch does later, and exits with status 1 if the run failed.

To try other lines without a new build, send your own maestro.toml (-c) or the generator it names (-g) from your computer. The server reads them against the repository as the build had it, and runs the build's image on the lines they make. Your files can have any name. A Dockerfile changes the image, so it takes maestro build -f.

maestro help concepts says what lines are.

Examples:

maestro run 12 --watch
maestro run 12 -c small.toml --watch
maestro run 12 -g genvrs.py
run=$(maestro run 12 -q) && maestro runs show "$run" --watch

Flags:

  -c, --config file         a file on your computer to make the lines from as maestro.toml, in place of the build's
  -g, --generator script    a generator script on your computer, in place of the one maestro.toml names
  -n, --interval duration   how often to redraw with --watch, at least 1s (default 2s)
      --json                print the queued run as JSON, and nothing else on standard output
  -q, --quiet               print only the number of the queued run, and nothing else on standard output
  -w, --watch               follow the run until it is over, and exit with status 1 if it failed

Cancel a run: drop what hasn't started and stop what has.

maestro runs cancel <run> [flags]

Flags:

maestro runs get

Download the files kept from a run.

maestro runs get <run> [dir] [flags]

Downloads every file kept from a run's containers into <dir>/<run>/<line>/, with what each container printed beside them, as stdout.log and stderr.log. <dir> is the current directory unless you give one. --line picks some lines only. Without --force, it won't download over a run already downloaded there.

Examples:

maestro runs get 31
maestro runs get 31 results/ --line 2 --line 5

Flags:

      --force    download over a run already downloaded there
      --line n   only line n (again for more)

maestro runs list

List your runs.

maestro runs list [flags]

Lists your runs, newest first. It shows your 20 newest, or as many as --limit says, and --limit 0 shows them all. --status (queued, running, succeeded, failed, cancelled) and --repo narrow the list, and --json prints the same runs. With --watch, it draws the list again every --interval until you press Ctrl-C. With --all, an administrator sees everyone's runs, and whose each one is.

Flags:

      --all                 everyone's runs (administrators only)
  -n, --interval duration   how often to redraw with --watch, at least 1s (default 2s)
      --json                print the runs as JSON
      --limit n             show the newest n runs, or all of them with 0 (default 20)
      --repo repo           only the runs of this repo, as owner/name or name
      --status status       only the runs with this status
  -w, --watch               keep showing it as it changes

maestro runs logs

Print what a line's container wrote to standard output and standard error.

maestro runs logs <run> [line] [flags]

Prints what a line's container wrote. What it wrote to standard output goes to your standard output, and what it wrote to standard error goes to your standard error, so you can tell the two apart or send them to different places. You can leave out the line of a run that has only one.

With -f, it waits for a line that hasn't started yet, and follows what a running line prints until the line ends, as tail -f does.

Once a line is over, all of its standard output comes before all of its standard error. Maestro doesn't keep how the two were interleaved as the container ran.

Examples:

maestro runs logs 31 2 -f
maestro runs logs 31 2 2>/dev/null   # only what it printed to standard output
maestro runs logs 31 2 >/dev/null    # only what it printed to standard error

Flags:

  -f, --follow   wait for the line to start, and follow what it prints until it ends
      --tail n   only the last n lines of a line still running (default: all)

maestro runs rm

Delete a finished run and the files kept from it.

maestro runs rm <run> [flags]

Also: remove.

Flags:

  -y, --yes    don't ask first

maestro runs show

Show each line of a run: where it ran, how it ended, what it kept.

maestro runs show [run] [flags]

Shows each line of a run: where it ran, how it ended and what it kept. Without a run, it shows your newest. With --watch, it draws the run again every --interval until the run is over or you press Ctrl-C, and exits with status 1 if the run failed.

Flags:

      --failed              only the lines that failed, ended in an error or were cancelled
  -n, --interval duration   how often to redraw with --watch, at least 1s (default 2s)
      --json                print the run as JSON
  -w, --watch               keep showing it as it changes, and exit with status 1 if the run failed

maestro settings

Show the server's settings: the image limit and how lines are scheduled.

maestro settings [flags]

Shows how many images each user may keep, and how the scheduler chooses whose line goes next and where: the policy of each of the three queues, the score's weights and how a user's share of the machines is measured. An administrator changes them on the Maestro page.

Flags:

      --json   print the settings as JSON

maestro top

Watch how loaded the machines are, like top.

maestro top [machine] [flags]

Shows one row for each machine: its CPU, memory, GPUs and load. Under CORES, 6/14 +3 means lines use 6 of the 14 cores the machine has for them and 3 more lines wait. The rows refresh every 2 seconds, or as often as -n says.

Press Enter on a machine to see its cores, memory, disks, network and GPUs, and the containers on it with whose each one is. Name a machine to open it straight away.

Anyone signed in sees the machines and their own containers. Administrators also see every container, and the server Maestro runs on, as "orq".

However many windows are open, Maestro reads each machine at most once every 2 seconds, and everyone watching shares that reading.

Flags:

  -n, --interval duration   how often to redraw, at least 1s (default 2s)

maestro usage

Show how much your lines have used.

maestro usage [flags]

Shows the core-hours and memory GB-hours your lines used over the last 30 days, or as many as --days says. A line counts when it ends. If an administrator set the scheduler up so, what you used counts against you when it chooses whose line goes next, and older usage counts less.

Administrators see everyone's usage, or one user's with --user, by their number or email.

Examples:

maestro usage --daily --days 7
maestro usage --user ana@example.org

Flags:

      --daily       a row for each day
      --days n      look back n days (default 30)
      --json        print the usage as JSON, a day at a time
      --user user   one user's usage, by their number or email (administrators only)
