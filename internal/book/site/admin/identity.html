Maestro

The identity provider

A Maestro deployment trusts one identity provider, which it talks to over standard OpenID Connect. orq sends the browser to the provider, checks the ID token that comes back, and then keeps a session of its own. The session is the maestro_session cookie, stored in Redis. No part of Maestro depends on a particular provider.

Registering Maestro

Register Maestro with your provider as a confidential client that uses the authorization code flow. The redirect URI is <orq>/api/auth/callback. In production orq is on the page's host, so the URI looks like https://maestro.example.org/api/auth/callback.

Then configure orq with these variables:

VariableDefaultMeaning
OIDC_ISSUERrequiredThe issuer URL. It must serve /.well-known/openid-configuration.
OIDC_CLIENT_IDrequired
OIDC_CLIENT_SECRETrequired
OIDC_REDIRECT_URLrequired<orq>/api/auth/callback, as registered with the provider
OIDC_SCOPESopenid email profileSeparated by spaces
OIDC_ROLES_CLAIMrolesThe ID token claim that holds the user's roles, as a string or a list. Some providers use groups.
OIDC_ALLOWED_ROLESemptySeparated by commas. When empty, anyone the provider authenticates can sign in.
VIEW_URLThe first of ALLOWED_ORIGINSWhere the Maestro page is served. Sign-ins return there.
REDIS_URLrequiredredis://[:password@]host:port/db of the Redis, Valkey or KeyDB that keeps sessions
SESSION_TTL12hHow long a Maestro session lasts
COOKIE_SECUREtrue, or false with MODE=devSet it to false only when you serve over plain http.

The page needs VITE_ORQ_URL, and optionally VITE_IDP_NAME for the label of the sign-in button.

Administrators

A user is an administrator in either of two cases: the provider puts one of OIDC_ADMIN_ROLES (by default ADMIN) in the user's roles claim, or the user's email is in ADMIN_EMAILS.

Administrators add machines, manage groups and the scheduler's settings, and see everyone's runs and containers.

Providers that have been tried

ProviderStatus
SaciAuthService (auth.logsad.com)Runs logsad.com's Maestro. Tested end to end.
DexRuns in the development stack.
Keycloak, Authentik, Zitadel and othersUntried.

An untried provider should work if it has OIDC discovery, the authorization code flow, PKCE with S256, and ID tokens signed with RS256 or ES256. Point OIDC_ROLES_CLAIM at the claim your provider puts roles or groups in.

Sessions and keys

Signing out of Maestro ends the Maestro session and leaves the user signed in at the provider. Signing out at the provider leaves an open Maestro session running until it expires.

The CLI doesn't use sessions. maestro login has the user approve a code on the page, and orq then gives the CLI a Maestro key of its own. orq stores only the key's hash.

A key can be revoked three ways. Its owner revokes it with maestro keys rm, maestro logout revokes the key it holds, and an administrator revokes every key of a user with Revoke keys in Admin › Groups. A revoked key stops working at once.

Whether a user is an administrator is read from their row in users on every request. That row is as fresh as their last sign-in on the page. A user removed at the identity provider keeps a working key until it is revoked, so revoke their keys when you remove them.
