Maestro

What Maestro is

Maestro runs a program many times on a group of shared machines and keeps what each run produces.

You keep the program in a git repository with a Dockerfile. Maestro clones the repository, builds a container image from it, and starts one container for each set of parameters you list. A hundred seeds become a hundred containers. Each container gets the cores and memory it asked for, on whichever machine has room for it first. When a container ends, Maestro keeps what it printed and the files it wrote. You download them, or read them in your browser.

The machines are shared, so everyone's containers wait in one queue. Users take turns in it, and an administrator chooses the rules that decide whose container starts next.

What you need

  • An account on a Maestro server. Your lab's administrator has its address.
  • The maestro command on your computer.
  • A git repository with a Dockerfile, on GitHub, GitLab, Codeberg or another Forgejo. The quickstart uses a public template, so you can start before you have one.

Quickstart: run the template

This page takes you from nothing to a finished run and its results. It uses maestro-template, a small public repository made for this, so you don't need a repository of your own yet.

1. Install the CLI

Download the package for your system from the maestro-cli releases and install it:

sudo dnf install ./maestro-*.x86_64.rpm     # Fedora, RHEL, Rocky, Alma
sudo apt install ./maestro_*_amd64.deb      # Debian, Ubuntu, Mint

Installing the CLI has the command for other systems, and for installing without root.

2. Sign in

maestro login

The first time, maestro asks for the address of your Maestro server and keeps it:

No Maestro server is set yet.
Maestro server URL (e.g. https://maestro.example.org): maestro.example.org
Kept. `maestro login --server <url>` changes it.

Then it prints a link and a short code:

To sign in to Maestro, open:

  https://maestro.example.org/?cli=KQ7M-W2HX

and approve this code:

  KQ7M-W2HX

Waiting for you to approve the code...

Open the link in any browser, sign in with your lab account if the page asks, and approve the code. The browser can be on another computer, which helps when you reach this one over SSH. The terminal then confirms:

Signed in to https://maestro.example.org as ada@example.com.

maestro login ends by offering to add a git forge. Answer n for now. The template is public, and Maestro needs a forge only to read private repositories.

3. Build and run the template

maestro build https://github.com/gustaleitcor/maestro-template --watch

This command clones the repository on the server, builds a container image from its Dockerfile, starts a run of that image, and follows the run until it is over. The build log streams to your terminal. These are the lines to look for in it:

Building github.com/gustaleitcor/maestro-template@main...
Cloning github.com/gustaleitcor/maestro-template@main...
Read maestro.toml: 2 container(s) on any machine, with 1 CPU and 512 MB each, keeping out.txt.
STEP 1/7: FROM docker.io/library/python:3.12-slim
…
Build #12 succeeded: 5d0c3a9f2e41…
Queued run 31 of build #12: 2 line(s) on any machine.
Keeping out.txt from each container.

The line that starts with Read maestro.toml says what a run of this build will do. The template's maestro.toml lists two sets of parameters, so the run has two containers. Maestro calls each one a line.

After the build, --watch draws the run and redraws it every two seconds:

Run 31 of gustaleitcor/maestro-template@main (build #12): running, on any machine
2 line(s): 1 assigned, 1 running

LINE  PARAMETERS                        MACHINE  STATUS    FILES
1     -t 10 out.txt                     Q1       running   -
2     -t 20 --label 'long run' out.txt  Q2       assigned  -

The numbers and machine names will be your server's. A line's status goes from queued to assigned while it waits, then running, then succeeded. The queue explains the waiting ones. The template's program sleeps for the number of seconds after -t, so the run takes under a minute once its lines start. The command returns when both lines have ended:

Run 31 of gustaleitcor/maestro-template@main (build #12): succeeded, on any machine
2 line(s): 2 succeeded

LINE  PARAMETERS                        MACHINE  STATUS     FILES
1     -t 10 out.txt                     Q1       succeeded  out.txt
2     -t 20 --label 'long run' out.txt  Q2       succeeded  out.txt

4. Look at what the run left

Each line keeps what its container printed and the files maestro.toml names, here out.txt. Use the run number from the previous step.

maestro runs logs 31 2     # what line 2 printed

long run: waiting 20s
done

maestro runs get 31        # download everything into ./31/

Downloaded 2 file(s) and the logs into 31

31/
├── 1/
│   ├── out.txt
│   ├── stderr.log
│   └── stdout.log
└── 2/
    ├── out.txt
    ├── stderr.log
    └── stdout.log

31/2/out.txt holds long run: done after 20s, the result the program wrote.

The same files are in the browser. Open your Maestro server's address, and the page shows your runs. Click run 31, then a line, and its files open beside it.

What happened

  1. Maestro cloned the repository and built an image from its Dockerfile. That is build #12.
  2. It read maestro.toml, which lists two lines of parameters and one file to keep.
  3. --watch started run 31 of that build, with one container for each line.
  4. Each container ran the image's program with its line as arguments, on a machine that had a free core and 512 MB.
  5. When a container ended, Maestro kept its output and out.txt, then removed the container.

A build and a run have separate numbers. maestro run 12 starts another run of the same image without building again, and maestro runs lists the runs you have.

Your own copy of the template

The quickstart ran the template as it is. To change what runs, you need the template in a repository you can push to. The chapters after this one all change that copy.

Make the copy

On GitHub, open maestro-template and press Fork. For another forge, or for a private copy, create an empty repository there and push the template into it:

git clone https://github.com/gustaleitcor/maestro-template my-experiment
cd my-experiment
git remote set-url origin <the address of your empty repository>
git push -u origin main

Let Maestro read it

A public copy builds the way the template did, by its address:

maestro build https://github.com/<you>/maestro-template --watch

A private copy needs a forge. A forge is how Maestro reaches the place your repositories live: its address and a read-only token of yours.

maestro forges add

The command asks which kind of forge it is (github, forgejo or gitlab), tells you which token to create and where, and checks the token before it keeps it. Git forges has the details.

With a forge added you can also name a repository by its short name, and maestro repos lists the ones your token can see:

maestro build maestro-template --watch          # a repository of yours
maestro build some-org/solver --ref v1.2.0      # someone else's, at a tag

Without --ref, a build takes the newest commit of the default branch.

  1. Edit a file.
  2. Commit and push.

The minimum: a Dockerfile

Maestro needs one file from a repository: a Dockerfile at its root. The Dockerfile says how to build an image that holds your program, and Maestro starts containers from that image.

The template's Dockerfile

FROM docker.io/library/python:3.12-slim

# Relative `outputs` are looked for here.
WORKDIR /work

COPY requirements.txt /app/requirements.txt
RUN pip install --no-cache-dir -r /app/requirements.txt
COPY . /app

# Your program. Each line of `parameters` replaces CMD and reaches it as
# arguments; -u prints as it goes, so logs can be followed.
ENTRYPOINT ["python", "-u", "/app/main.py"]

# Used when maestro.toml has no lines.
CMD ["-t", "1", "out.txt"]

Three of its instructions decide how Maestro runs the image.

InstructionWhat Maestro does with it
ENTRYPOINTThe program every container starts. Maestro never changes it.
CMDThe arguments the program gets when a run supplies none. A line of parameters replaces it.
WORKDIRThe directory the program starts in. A relative path among the files to keep is looked for here.

So the template's containers run python -u /app/main.py followed by either a line of parameters or, when there are none, -t 1 out.txt.

Write ENTRYPOINT as a list, as above. Written as plain text (ENTRYPOINT python /app/main.py), it runs through a shell that drops the arguments, and every line would run the program with none.

The rest of the Dockerfile is yours. Any language works, because Maestro only starts the container. A compiled program can be built in one stage and copied into a small image:

FROM docker.io/library/gcc:14 AS build
WORKDIR /src
COPY . .
RUN make solver

FROM docker.io/library/debian:bookworm-slim
WORKDIR /work
COPY --from=build /src/solver /usr/local/bin/solver
ENTRYPOINT ["solver"]
CMD ["--help"]

What a Dockerfile alone gets you

A repository with a Dockerfile and no maestro.toml builds and runs. The build log says what its runs will do:

No maestro.toml; runs will use the default: 1 container running the image's own command on any machine, with 1 CPU and 512 MB each, keeping only its logs.

A run of that build is one line:

Run 32 of ada/maestro-template@main (build #13): succeeded, on any machine
1 line(s): 1 succeeded

LINE  PARAMETERS         MACHINE  STATUS     FILES
1     (image's command)  Q1       succeeded  -

That is one container, started with the image's own CMD, with 1 core and 512 MB, on any machine. Maestro keeps what it printed and no files, so the out.txt the program wrote is gone with the container.

This is enough to run one long job on the lab's machines. To run the program many times with other arguments, to give it more cores or memory, or to keep its files, add a maestro.toml.

You can see this with your copy of the template: delete maestro.toml, push, and build. Put the file back afterwards, because the next chapter starts from it.

Where Maestro looks for the Dockerfile

Maestro builds the Containerfile at the root of the repository, or else the Dockerfile there. To build from a file somewhere else, name it in maestro.toml with dockerfile.

The root of the repository is the build's context wherever the Dockerfile is, so the paths in COPY start at the root.

A repository with neither file doesn't reach the server. maestro build stops and says that it has no Dockerfile.

What goes into the image

COPY . /app copies the repository into the image, except what .dockerignore lists. The template's .dockerignore leaves out caches, the README, and also maestro.toml and genvrs.py. Maestro reads those two from the repository when it builds. The program never needs them.

Maestro's clone has no .git directory. Git keeps the forge token there, and the token would end up in the image. A RUN git rev-parse HEAD in a Dockerfile therefore fails. The Maestro page shows which commit a line's image was built from.

A smaller image starts sooner. The first time a line runs on a machine, Maestro copies the image there, and the line waits for the copy.

How long a build takes

Every build runs every step of the Dockerfile again. Maestro keeps no layers from earlier builds, so installing dependencies takes the same time each time. A build that runs longer than the server allows, 30 minutes unless the administrator changed it, fails.

Changing only the parameters doesn't need a build. maestro run <build> -c maestro.toml runs an image you already have on other lines, as Trying a change without pushing it explains.

Printing as the program runs

The template starts Python with -u, which turns off output buffering. Without it, Python holds back what the program prints until a buffer fills, and maestro runs logs <run> <line> -f shows nothing for a long time. In other languages, flush standard output after each line you want to see.

maestro.toml: how the image is run

maestro.toml is an optional file at the root of the repository, beside the Dockerfile. It says how many containers a run starts and with which arguments, how much of a machine each one may use, and which files to keep.

Every key is optional. A key you leave out keeps the default from the previous chapter: one container, the image's own command, 1 core, 512 MB, any machine, no files.

This is the template's file, with its comments removed:

parameters = [
  "-t 10 out.txt",
  "-t 20 --label 'long run' out.txt",
]

outputs = ["out.txt"]

Maestro reads maestro.toml when it builds the repository and keeps the result with the build, so every run of a build has the same lines. To change them, push the change and build again, or send the file with a run.

The sections below add one key at a time. Each can be tried on your copy of the template: edit, push, and maestro build <your copy> --watch.

parameters

Each string is one line, and a run starts one container for each line. The line's words replace the image's CMD, so the program receives them as its arguments. The template's two lines start these two containers:

python -u /app/main.py -t 10 out.txt
python -u /app/main.py -t 20 --label 'long run' out.txt

Maestro splits a line into words at spaces. Single quotes, double quotes and backslashes keep words together the way they do in a shell, so 'long run' reaches the program as one argument. Nothing else is special, because no shell runs the line. A $HOME or a * reaches the program as typed. A program that needs a shell can be a shell script.

Add a third line, and the next build says 3 container(s):

parameters = [
  "-t 10 out.txt",
  "-t 20 --label 'long run' out.txt",
  "-t 5 --label quick out.txt",
]

A run has at most 1000 lines. When a list gets long or follows a pattern, a generator can compute it.

outputs

outputs = ["out.txt", "results/", "plots/summary.png"]

These are the files Maestro copies out of each container when it ends, whether the program succeeded or failed. Each path is a path inside the container. A relative one starts at the image's WORKDIR, which is /work in the template. A directory is kept with everything in it.

A file the program didn't write is listed as missing, and the line's status doesn't change because of it.

What the container prints is always kept, as stdout.log and stderr.log, whatever outputs says. What a line leaves behind shows where everything ends up.

cpus and memory

cpus   = 4      # whole cores; default 1
memory = 8192   # MB; default 512

These two numbers do two jobs.

They limit the container. It can use the processor time of cpus cores and no more. If it takes more memory than memory, the kernel kills it, and the line ends failed, usually with exit code 137.

They also decide where and when the line starts. A machine starts a line only when that many cores and that much memory are free on it. A smaller request fits on more machines and starts sooner. Maestro refuses a run when one of its lines would not fit on any machine it may use, even an empty one:

line 3 asks for 64 cpus and 512 MB, which no machine it may use has for lines even with nothing else on it (see `maestro machines list`)

maestro machines shows what each machine has. A program doesn't learn its limit by counting the machine's cores, so read how many threads to start before giving a multithreaded program more than one core.

env

env = { SEED = "42", MODE = "fast" }

These variables are set in every container's environment. A name is made of letters, digits and _, and can't start with a digit. It also can't start with MAESTRO_, which is reserved for the variables Maestro sets itself.

Don't put secrets in env. Maestro stores the environment with the run and shows it on the line's page.

machines

machines = ["Q1", "Q2"]

The lines run only on these machines. The names come from maestro machines, and upper or lower case doesn't matter. A name that doesn't exist refuses the run.

Leave machines out unless the program needs particular hardware. With no machines, a line starts on whichever machine has room first.

outputs_layout

outputs_layout = "shared"   # default: "per-line"

With per-line, each line's outputs go in a directory of its own, <run>/<line>/<path>. Two lines can both write out.txt and both files are kept.

With shared, every line's outputs go into one tree for the whole run, <run>/shared/<path>. This suits a program whose lines each fill in part of one results directory, such as results/<instance>/<seed>.json. When two lines write the same path, the one Maestro collects last overwrites the other, so give each line paths of its own. Logs stay separate for each line in both layouts.

dockerfile

dockerfile = "docker/Dockerfile"

Maestro builds the image from this file. The path starts at the root of the repository and must stay inside it. The root remains the build's context, so COPY paths in that Dockerfile still start at the root.

generator

generator = "genvrs.py"

This names a Python script in the repository that computes lines. They come after the lines of parameters, and the script can give each of its lines its own cpus, memory, env and outputs. The next chapter is about it.

When the file is wrong

An invalid maestro.toml fails the build, and the last lines of the build log say why. A misspelt key is an error too, so that a typo isn't silently ignored:

maestro.toml: unknown key "paramters" (known: machines, parameters, generator, dockerfile, outputs, outputs_layout, cpus, memory, env)

maestro.toml keys lists every key with its default and its limits on one page.

Generating lines with Python

Writing lines by hand works for a few of them. A grid of parameters, or one line for each instance file, is easier to compute. A generator is a Python script in the repository that defines a function called genvrs. Every string the function yields becomes one line, split into words the same way a line of parameters is.

Turn on the template's generator

The template already has one, genvrs.py:

def genvrs():
    for seconds in (10, 20, 30):
        yield f"-t {seconds} out.txt"

Its maestro.toml has the line that enables it commented out. Remove the #:

generator = "genvrs.py"

Push and build. The build log now counts five containers:

Read maestro.toml: 5 container(s) (3 from genvrs.py) on any machine, with 1 CPU and 512 MB each, keeping out.txt.

The two lines of parameters come first, then the three the generator yielded. If you delete parameters, the generator's lines are the whole run.

A grid of parameters

import itertools
from collections.abc import Generator

def genvrs() -> Generator[str]:
    for t, seed in itertools.product([10, 20, 30], range(3)):
        yield f"-t {t} --seed {seed} out.txt"

This yields nine lines, from -t 10 --seed 0 out.txt to -t 30 --seed 2 out.txt.

One line for each file

The script can read the repository's files, so it can list a directory of instances. This is a shortened version of what the template's knapsack branch does:

from pathlib import Path

INSTANCES = Path(__file__).parent / "instances"

def genvrs():
    for path in sorted(INSTANCES.glob("*.txt")):
        yield f"{path.stem} --time-limit 60"

Lines that need different settings

By default every generated line runs with the cpus, memory, env and outputs of maestro.toml. To change them for some lines, define a class called Config above genvrs and assign to its attributes before yielding. Each line runs with what the class holds at the moment the line is yielded.

class Config:
    outputs: list[str] | None = None     # None: what maestro.toml says
    cpus: int | None = 4                 # 4 cores, whatever maestro.toml says
    memory: int | None = None
    env: dict[str, str] | None = None

def genvrs() -> Generator[str]:
    yield "-t 10 small"          # 4 cores, maestro.toml's memory
    Config.memory = 4096
    for seed in range(3):
        Config.env = {"SEED": str(seed)}
        yield "-t 10 large"      # 4 cores, 4096 MB, SEED 0, 1 and 2
    Config.memory = None
    yield "-t 10 medium"         # 4 cores, maestro.toml's memory again

None means "what maestro.toml says, or the default if it says nothing". The class may hold only these four attributes. machines is the same for every line and is set in maestro.toml.

Where and when the script runs

Maestro runs the script once, during the build, and the build keeps the lines it yielded. Every run of that build has the same lines. A script that draws random numbers should seed them (random.Random(2026)), so that building the same commit twice gives the same lines.

The script runs inside the Maestro server, in a sandbox, and not in your image. The sandbox is a Python 3.14 with the standard library and nothing else. That has consequences:

  • Packages from requirements.txt aren't there, and neither is anything that needs compiling, such as numpy.
  • The script can read the repository's files and import its other modules. It can't write files.
  • It has no network and no environment variables.
  • It gets 256 MB of memory and 30 seconds.

What the script prints goes to the build log, which makes print a good way to check what it computed.

What fails the build

The build fails, and the log says why, when the script:

  • raises an exception, or runs past its 30 seconds
  • doesn't define genvrs
  • yields nothing
  • yields something that isn't a string
  • brings the run to more than 1000 lines, counting those of parameters
  • sets a Config attribute to a value maestro.toml wouldn't accept, or sets one that isn't a setting
genvrs yielded a int as item 4; every item must be a string
Config.machines isn't a setting; Config may only hold outputs, cpus, memory, env

Trying a generator without building

maestro run <build> -g genvrs.py runs an image you already have on the lines of a script from your computer. Nothing is pushed or built. See Trying a change without pushing it.

Inside the container

Each line runs as one container of your image. Maestro starts the image's ENTRYPOINT in its WORKDIR, with the line's words as arguments in place of CMD. The container gets the cores and memory the line asked for. When it ends, Maestro keeps its logs and outputs and removes it.

What Maestro tells the program

Maestro sets these variables in every container, after those of env:

VariableValue
MAESTRO_RUNThe run's number
MAESTRO_LINEThe line's number in the run, starting at 1
MAESTRO_CPUSThe line's cpus
MAESTRO_MEMORYThe line's memory, in MB
MAESTRO_OUTPUTSThe line's outputs, one path on each text line

How many threads to start

A limit on cores doesn't change how many cores a program sees. nproc, os.cpu_count() and most libraries still report every core of the machine. A program that starts one thread for each core it sees starts far more threads than it has cores to run them on, and gets slower.

Read MAESTRO_CPUS and start that many. The template's knapsack branch does it for its solver:

import os

# As many threads as the container has cores; outside Maestro, 0 lets the
# solver choose.
model.threads = int(os.environ.get("MAESTRO_CPUS", "0"))

Most solvers have an option for this, such as Gurobi's Threads, CPLEX's threads and num_workers in OR-Tools. Programs built on OpenMP read OMP_NUM_THREADS, which a small start script can set from MAESTRO_CPUS before it starts the program.

What happens when memory runs out

When a container takes more memory than its memory, the kernel kills it. The line ends failed, usually with exit code 137. Ask for what the program needs at its largest, plus some room. A smaller request starts sooner, but a line that is killed has to run again from the start.

Machines that can't limit cores

Some machines can't enforce the limit on cores. This happens when Podman runs without root and the system doesn't give it the cpu cgroup controller, which is the default on Ubuntu 22.04. On such a machine a line still counts as using its cpus, and MAESTRO_CPUS is still set, but a program that starts more threads does take more cores and slows the lines beside it. An administrator can fix the machine once, as Adding machines describes.

Files and logs

Write results to the paths that outputs names. Everything else in the container is gone when it ends.

Maestro keeps what the program prints as stdout.log and stderr.log, and maestro runs logs <run> <line> -f shows it while the line runs. Python buffers its output when it isn't writing to a terminal. Start it with -u, set PYTHONUNBUFFERED=1 in the image, or print with flush=True.

Maestro keeps up to 1 GB of logs and outputs for each line, unless your administrator set another limit. It drops the rest and notes that on the line.

How the exit code becomes a status

A line is succeeded when its program exits with 0 and failed when it exits with anything else. maestro runs show <run> --failed lists the lines that didn't succeed.

A line that ends error never ran to the end for a reason outside your program. Most often it couldn't start on its machine, or the machine restarted while it ran and the container was lost. Run it again.

Trying a change without pushing it

Committing and pushing for every experiment with maestro.toml gets slow. maestro build and maestro run can take three files from your computer and use them in place of the repository's:

FlagReplaces
-c <file>maestro.toml at the root of the repository
-g <file>The generator that maestro.toml names. When it names none, the script is added at the root under its own name and used.
-f <file>The Dockerfile that maestro.toml names, or else Dockerfile at the root. Only maestro build takes it.

The file on your computer can have any name.

maestro build my-app -c bench.toml -g genvrs.py -f Dockerfile   # a new image
maestro run 81 -c small.toml --watch                            # build #81's image, other lines

With a run: other lines, same image

maestro run <build> -c or -g doesn't build anything. The server clones the repository again at the commit the build was made from, puts your files over the clone, runs the generator there, and starts the build's image on the lines that result. It takes seconds, because no image is built.

Use it to try other parameters, other cpus and memory, other machines or another seed. For a private repository the CLI sends the forge token it has, so the server can clone.

A run doesn't take -f, and it ignores a dockerfile key in the maestro.toml you send, because it builds no image.

With a build: a new image

maestro build puts your files over its clone before it reads anything, so the image is built with them. Use it when the Dockerfile changes.

A change to the program itself still has to be pushed. These flags replace only the three files above.

How Maestro records it

The lines of such a build or run don't come from the commit alone, so maestro builds and maestro runs show say which files you sent.

What you send is checked the way a build checks the repository's files, and an invalid file fails the build or refuses the run. A file can be at most 1 MiB.

Fuller examples

The template's default branch is as small as a working repository can be. Two other branches of the same repository use more of what the previous chapters covered. --ref builds a branch:

maestro build https://github.com/gustaleitcor/maestro-template --ref knapsack

Both branches name the machines of the lab they were written for in machines. On another Maestro, a run of them is refused because those machines don't exist. Fork the repository and remove the machines line, or start the run with a maestro.toml of your own: maestro run <build> -c my.toml.

knapsack: a solver job

This branch solves knapsack problems with the mip solver, one container for each instance and capacity.

FileWhat it shows

genvrs.pyReads every file in instances/ and yields three lines for each, with the capacity scaled by 0.25, 0.5 and 2

The generator gives larger instances more than the rest. An instance with more than 30 items gets 1024 MB through Config.memory and a time limit of 60 seconds, where a small one keeps maestro.toml's 512 MB and gets 10 seconds. It also prints one line for each instance, which shows up in the build log.

With three instance files, a run has eleven lines: two from parameters and nine from the generator.

stress: a thousand lines

This branch is a stress test of the queue. Its containers do no useful work. Each one sleeps, keeps its cores busy, fills part of its memory, or does both, for between ten seconds and four minutes, and writes a report.json with what it used.

maestro.toml lists four lines and genvrs.py adds 996, which makes 1000, the most a run can have. One line in ten also keeps a samples.csv, and every hundredth line exits with code 3 on purpose, so the run has failed lines to look at.

It is a good run to have going while you read The queue:

Installing the CLI

The CLI is one program, maestro. Every release has packages for Linux and a plain binary for Linux, macOS and Windows on the maestro-cli releases page.

With a package

A package installs maestro in /usr/bin, with its shell completions:

sudo dnf install ./maestro-*.x86_64.rpm                            # Fedora, RHEL, Rocky, Alma
sudo zypper install --allow-unsigned-rpm ./maestro-*.x86_64.rpm    # openSUSE

sudo apk add --allow-untrusted ./maestro_*_x86_64.apk              # Alpine

On an ARM machine, take the aarch64 or arm64 package.

Without root, or on macOS and Windows

The .tar.gz archive (.zip on Windows) holds the same binary, which needs nothing else installed. Unpack it and put maestro in a directory on your PATH, such as ~/.local/bin.

Shell completions

The packages install completions for bash, fish and zsh. With the plain binary, write them yourself:

maestro completion bash > ~/.local/share/bash-completion/completions/maestro
maestro completion fish > ~/.config/fish/completions/maestro.fish
maestro completion zsh  > "${fpath[1]}/_maestro"

Completions offer your own builds, runs, machines and repositories. maestro run <TAB> lists your builds, each with the repository it was built from. They ask the server, so they work once you have signed in.

Checking the install

maestro --version
maestro docs

maestro docs opens this book from the copy inside the binary, which is a quick way to confirm the binary on your PATH is the one you installed.

Signing in

Maestro has no passwords of its own. It signs you in through your lab's identity provider, with the account you use for the lab's other services.

In the browser

Open the Maestro page and press the sign-in button. The identity provider asks for your account, and sends you back signed in. A session lasts 12 hours unless your administrator set another length.

Signing out of Maestro ends the Maestro session and leaves you signed in at the identity provider. Signing out there doesn't end a Maestro session that is already open.

In the terminal

maestro login

maestro login prints a link to the Maestro page and a short code. Open the link, sign in there if the page asks, and approve the code. The CLI then receives a key of its own and uses it for every command.

A key expires 90 days after it was issued, unless your administrator set another length. After that, commands say "this Maestro key expired; run maestro login", and maestro login gives you a new one.

The CLI doesn't open the link for you. You can open it in a browser on another computer, which is how you sign in on a machine you reach over SSH.

Where the key is kept

The CLI stores the key in your system's keyring. On a machine without a keyring, or one whose keyring asks for a password each time, sign in with:

maestro login --store-in-file

The key then goes into the CLI's config file, which only your user can read.

Which server the CLI talks to

The CLI has no built-in server. The first time a command needs one, maestro asks for its address and keeps it. An address without a scheme gets https://.

To use another Maestro, sign in to it:

maestro login --server https://maestro.example.org

Every later command talks to that server. For one command only, pass --server, or set MAESTRO_ORQ_URL. The flag wins over the variable, and the variable wins over the server the CLI kept.

The CLI stores the key together with the server that issued it and sends it nowhere else. If you point a command at a different server, the CLI tells you to sign in there.

maestro with no arguments shows who is signed in, on which server, and on which forges.

Your keys

Each maestro login issues a new Maestro key, for the computer you run it on. To see the keys you have:

maestro keys

It lists each key by its prefix, the first 10 characters, with when it was created and when it expires. It marks the key this computer uses.

If you no longer trust a computer you signed in on, revoke its key from another one:

maestro keys rm mk_Q3xv9aZ

The key stops working at once, on every computer that holds it. The command asks first. With --yes it doesn't ask.

An administrator can revoke every key of a user, from Admin › Groups on the Maestro page.

Signing out

maestro logout

This revokes the key on the server that issued it. Then it removes the key, the server address and every forge token from this computer.

If the server can't be reached, maestro logout still forgets the key, and says that the key is still valid on the server. Revoke it later with maestro keys rm from a computer that is signed in.

maestro logout changes nothing on the forges, so revoke a token there if you no longer trust the computer it was on.

Git forges

A forge is the place your repositories live, such as GitHub or Codeberg. Maestro needs a forge only to read private repositories, and to let you name a repository without typing its whole address. A public repository on GitHub, GitLab or Codeberg builds from its address with no forge at all.

To Maestro, a forge is the address of its API and a read-only token of yours. The CLI keeps the token on your computer and sends it to the server with each build that needs it. Maestro uses it to list and clone repositories. A forge never signs you in to Maestro.

maestro forges add          # add one: asks for the kind and the token
maestro forges              # the forges you have
maestro repos               # the repositories they can see
maestro forges rm <name>    # forget one

The kinds of forge

githubgithub.comA classic token with the repo scope
forgejoCodeberg, or any Forgejo or Gitea server with --urlRepository: Read and User: Read, everything else at No access

maestro forges add tells you how to create the token. For GitHub and GitLab it prints a link that fills in the form. It checks the token before keeping it.

On GitHub, use a classic token. A fine-grained token reaches the repositories of one owner only, so it can't read a private repository that belongs to someone else and that you collaborate on.

Naming a repository

maestro build accepts a name, an owner/name, or an address:

maestro build my-app                                 # yours, on your forge
maestro build some-org/my-app --ref v1.2.0           # someone else's, at a tag
maestro build https://codeberg.org/some-org/my-app   # by address

Maestro uses the forge that has the repository. When more than one has it, choose with --forge.

Your lab's own Forgejo

Add it with its address:

maestro forges add --kind forgejo --url https://git.example.org

The server clones only from hosts its administrator allows. By default those are github.com, codeberg.org and gitlab.com, so an administrator has to add your lab's host to ALLOWED_FORGE_HOSTS first (Environment variables).

Browsing repositories

In a terminal, maestro repos is a full-screen list of one forge's repositories. The left and right arrows switch to another forge, and --forge chooses the one shown first. With --json, or when its output goes to a pipe, it prints every forge's repositories once.

How the CLI behaves

A few rules hold for every maestro command. Knowing them saves looking up each command separately.

Listing and removing

Anything there can be several of has a command in the plural. Given nothing else, it lists them: maestro builds, maestro runs, maestro machines, maestro repos and maestro forges.

Removing is always rm, as in maestro runs rm 31. It asks before it removes. A script has no terminal to answer at, so there it needs --yes.

The names older versions used still work: image, machine, repo and forge for the plurals, and remove for rm.

Build numbers and run numbers

A build's number is written #12 and a run's is written run 31. They count separately, so build #12 and run 12 are unrelated. maestro run takes a build, and maestro runs show takes a run. maestro builds run 12 does the same as maestro run 12.

Output for scripts

Every list takes --json. It prints the same things the table shows, under the names the server uses.

maestro build and maestro run take --json too, and -q, which prints only the number of what they made. With either flag, standard output holds the answer alone, and progress messages go to standard error:

run=$(maestro run 12 -q) && maestro runs show "$run" --watch

Exit status

StatusMeaning
0The command did what it was asked.
1Something failed. This includes a run followed to its end with --watch that failed or was cancelled.
2The command was written wrongly. maestro says so before it contacts the server.
130Ctrl-C stopped it.

Colours

--no-color, or NO_COLOR=1 in the environment, prints without colours. Output sent to a pipe or a file has none in any case.

Help

maestro --help lists the commands grouped by purpose, and maestro <command> --help describes one. Each help text ends with the maestro docs topic that explains the command in this book. maestro help concepts prints a short version of the glossary in the terminal.

Builds and images

A build turns one commit of a repository into a container image. Runs start from builds, so a build comes first.

maestro build my-app                  # build the default branch
maestro build my-app --ref v1.2.0     # a branch, a tag or a commit
maestro build my-app --run            # build, then start a run
maestro build my-app --watch          # build, start a run, follow it to the end
maestro builds                        # the builds you have
maestro builds rm 12                  # remove a build's image

What a build does

  1. The server clones the repository at the commit you asked for.
  2. It reads maestro.toml and runs the generator, if there is one. The lines that result are stored with the build.
  3. It builds the image from the Dockerfile.

The build log streams to your terminal while this happens. Ctrl-C stops the build on the server too. When a build fails, the last lines of the log say why. The usual causes are a step of the Dockerfile, an invalid maestro.toml, and a generator that raised an exception.

A finished build has a number, written #12. maestro run 12 starts a run of its image.

You can have 2 builds running at once, unless your administrator set another number. Maestro refuses a third with "you already have 2 builds running; wait for one to end".

How many images you keep

You keep at most 10 images, unless your administrator set another number. When a new build would exceed it, Maestro removes the image you ran least recently. An image you never ran counts by when it was built, and an image a run is still using is never chosen.

Removing an image keeps the build's record, its runs and their files. To run that commit again, build it again. maestro builds rm <build> removes an image by hand to make room.

Images on the machines

An image is built on the server. The first time one of its lines is given to a machine, Maestro copies the image there, compressed on the way, and the line stays assigned until the copy is done. The image then stays on that machine, so later runs of the same build start without the copy.

A smaller image copies faster. A -slim base image and a .dockerignore that leaves out what the program doesn't use both help.

Runs and lines

A run starts one container for each line of a build. Each line runs once, on the first machine it is allowed on that has room for it.

maestro run 12 --watch          # start it and follow it to the end
maestro runs                    # your newest runs
maestro runs show 31            # the lines of run 31
maestro runs logs 31 2          # what line 2 printed
maestro runs get 31             # download the outputs and logs
maestro runs cancel 31          # stop it
maestro runs rm 31              # delete it and its files

Following a run

--watch redraws the output in place every 2 seconds, or as often as --interval says. It works on maestro run, maestro runs show and maestro runs list.

maestro runs show <run> --watch returns when the run is over. It says how the run ended and exits with status 1 if the run failed or was cancelled, so a script can wait on it. Ctrl-C stops the watching and leaves the run alone. When the output goes to a pipe, --watch prints a new copy only when something changed.

Reading logs

maestro runs logs <run> <line> prints what the line wrote to standard output on your standard output, and what it wrote to standard error on your standard error. Redirect one away to read the other:

maestro runs logs 31 2 2>/dev/null     # standard output only

A run with a single line doesn't need the line number.

-f follows the line the way tail -f follows a file. It waits for a line that hasn't started, prints what a running line prints as it comes, and returns when the line ends.

For a line that has ended, all of its standard output comes before all of its standard error. Maestro stores the two apart and doesn't record how they were interleaved.

Downloading

maestro runs get <run> downloads every line's outputs and logs into a directory named after the run. What a line leaves behind describes the layout. --line picks lines, a second argument picks the directory, and --force downloads over a run that is already there.

Cancelling and deleting

maestro runs cancel <run> drops the lines that haven't started and stops the ones that are running. Lines that had already ended keep their status.

maestro runs rm <run> deletes the run with all its logs and files. It asks first.

How a line ends

StatusWhat happened
succeededThe program exited with 0.
failedThe program exited with another code, or the kernel killed it for using more memory than the line asked for.
errorThe line couldn't run. Most often it couldn't start on its machine, or the machine restarted while it ran and the container was lost.
cancelledYou cancelled the run before the line ended.

A line runs for at most a week, unless your administrator set another length. When a line runs longer, Maestro stops it, keeps its logs and outputs, and ends it as error with the note "stopped after 168 hours, the longest a line may run on this server".

Any other error comes from the system and says nothing about your program. The Maestro page shows such lines in amber with the reason, and you can run them again.

A machine that stops answering doesn't turn its waiting lines into errors. Maestro moves them back to queued so another machine can take them. Lines already running on that machine are left alone and checked again when it returns.

What a line leaves behind

When a container ends, Maestro keeps what it printed and the files that outputs names, then removes the container. Everything else the program wrote inside it is gone.

The layout of a download

maestro runs get <run> downloads a run into a directory named after it, with one directory for each line:

31/
├── 1/
│   ├── report.json
│   ├── stderr.log
│   └── stdout.log
├── 2/
│   └── …
└── shared/          (with outputs_layout = "shared")
    └── results/…

A run downloaded from the Maestro page comes as a zip with the same layout.

Logs

Maestro keeps standard output and standard error apart, as stdout.log and stderr.log in the line's directory. Both files exist even when the program printed nothing to one of them.

The two names are reserved. If outputs lists a file called stdout.log or stderr.log, Maestro keeps the log and drops the program's file.

Runs made before Maestro kept the two streams apart have both in one file, <line>.log, beside the line's directory. Maestro still reads those.

Outputs

Maestro copies each path in outputs out of the container. A directory comes with everything in it. Only regular files and directories are kept, so symbolic links, devices and similar entries are skipped.

An output the program didn't write is listed as missing, as in out.txt (missing) under FILES in maestro runs show.

With outputs_layout = "shared", the outputs of every line go into one tree for the run, under shared/. When two lines write the same path, the one Maestro collects last overwrites the other.

How much is kept

Maestro keeps up to 1 GB of logs and outputs for each line, unless your administrator set another limit with RUN_OUTPUT_MAX_MB. It drops what goes over, and the line carries a note that its logs or outputs were cut.

How long it is kept

A run's files stay until you delete the run with maestro runs rm <run>. Maestro deletes none of them on its own. Removing a build's image to make room for a newer build keeps the build's runs and their files.

Where the files are on the server

An administrator finds the same files under the server's data directory:

/maestro/data/<user>/<run>/<line>/stdout.log
/maestro/data/<user>/<run>/<line>/stderr.log
/maestro/data/<user>/<run>/<line>/<file>
/maestro/data/<user>/<run>/shared/<file>     (with outputs_layout = "shared")

Where the numbers come from

The server reads a machine by running one small shell script over SSH. The script reads /proc and df, and nvidia-smi when the machine has it. The server asks Podman for the containers' usage. GPUs are read only when they are NVIDIA's and the machine runs Linux.

Some machines let the server's SSH user reach the Podman socket and nothing else. Such a machine still appears with its containers, and says why it has no other numbers.

The server keeps each reading for 2 seconds and shares it among everyone watching. However many maestro top windows are open, each machine gets one SSH connection every couple of seconds. The cores lines take and the lines waiting come from the server's own records, so they are always current.

Usage can count against you in the queue. An administrator can set the scheduler to weigh what each user used recently when it decides whose line goes next, with older usage counting less. This is the decay measure in Policies and the score.

maestro export

maestro export writes a CSV with one row for each line of the runs you queued over a period. A row has the line's run and number, its cores and memory, the machine it ran on, its status, and the times it was submitted, assigned, started and finished. orq, the server

orq makes every decision in Maestro. It signs people in through the lab's identity provider, clones repositories with the forge tokens the CLI sends it, and builds images with its own Podman. It records every build, run and line in a SQLite database.

orq also runs the scheduler. The scheduler is a loop that picks which waiting line goes to which machine, copies images to the machines, starts containers, and collects what they leave.

Because everything about a run is in the database, orq can restart in the middle of one and continue from where it stopped.

The view

The view is the Maestro page, a web page served from the same host as orq. It shows your runs and their files, the queue, your usage, and the admin pages. It keeps no state of its own and asks orq for everything it shows.

The CLI

The CLI is the maestro command, which does everything from a terminal. On your computer it keeps the server's address, your Maestro key and your forge tokens.

The machines

A machine is a computer with Podman and an SSH server. It needs no Maestro software. orq connects to each machine over SSH and talks to the machine's Podman socket through that connection. It copies images to the machine, starts containers, reads how loaded the machine is, and takes the logs and outputs back when a container ends.

orq removes a container once it has the container's logs and outputs. The image stays on the machine, so the next run of the same build starts without copying it again.

The queue

The machines are shared, so a line usually waits before it runs. It waits in three places in turn, and maestro queue shows how many lines are in each.

maestro queue      # how many lines wait in each queue, yours and everyone's

A line in the dispatcher queue is still queued. Being a head isn't a status: the scheduler works your head out again on every pass.

The user queue: your head

maestro run puts every line of the run in your user queue. The user policy puts your queued lines in an order, and the first of them is your head. By default it is the oldest run first, line by line. With lcfs or pq, a line you queue later can take your head's place.

A line that no machine could hold, even an empty one, is never your head. It waits without holding back your other lines.

Each group has a dispatcher queue, made of the heads of its users and nothing else. It has no size of its own: it holds one line for each user who has lines waiting.

Groups take turns at the machines, one line a turn. In its turn, a group's dispatcher policy picks one of its heads and gives it to a machine. The machine has to be one the line may run on, by its machines, and it has to have room in its queue. Only three lines wait on each machine by default. When several machines qualify, the scheduler draws one at random. A group with no head that can go anywhere passes its turn.

Once your head is given a machine, your next line is your head. The dispatcher policy can be as simple as the oldest head, or it can weigh how much of the machines each user already holds.

While the line waits on the machine, the server copies the line's image there if the machine doesn't have it yet.

The machine queue: from assigned to running

A machine starts a waiting line when the line's cores and memory fit in what the machine has free. The machine policy picks which of the lines waiting on the machine starts first.

Why the queues on machines are short

A machine holds only three waiting lines, so the scheduler decides whose line goes next as late as it can. Someone who queues a single line behind another user's thousand doesn't wait for the thousand. Nearly all of those are still in their user queue, and the single line is its user's head at once.

Each user's head is chosen by fifo. In a group's turn, fifo picks one of its heads and gives it to a machine drawn among those with room. Lines start by fifo on each machine.

The first row is yours and the everyone row is the total. HEADS is how many of the QUEUED lines are heads, in the dispatcher queue: yours is 1 while you have a line some machine could hold. SHARE is how much of what all users hold is yours, as the scheduler measures it. The second table shows your group: its queued lines, the heads among them, which make its dispatcher queue, and its assigned lines. The last line names the three policies in force.

The Maestro page shows the same under Queue and reads it again every 5 seconds.

Why a line is waiting

Many lines queued

Only your head competes for a machine, and the dispatcher policy chose other users' heads before it. Under a policy that weighs shares, a user who holds less of the machines than you goes first. Your other lines wait their turn behind your head.

Your head waits in the dispatcher queue

Either the machines' queues are full or it is another group's turn. A line with machines = [...] waits for room on those machines only.

A line assigned for a long time

The machine doesn't yet have the cores and memory the line asked for, or the line's image is still being copied there. The copy happens only for the first line of a build on each machine.

A large line waits while smaller ones start

Most machine policies, such as fifo-skip and best-fit, choose among the lines that fit in the free space now, so smaller lines go around a large one that doesn't fit yet. Under fifo, which is the default, the oldest line holds back the ones behind it until it fits.

maestro top shows how much of each machine lines are using and how many lines wait there, as in 6/14 +3. Watching the machines explains the columns.

Waiting less

  • Ask for the cores and memory the program needs and no more. A line starts only where its cpus and memory fit, so a smaller line fits on more machines and sooner.
  • Leave machines out unless the program needs particular hardware.
  • Keep the image small. The first line of a build on each machine waits while the image is copied.

When a machine goes away

A machine the server can't reach, over SSH or at its Podman socket, gets no new lines. The lines that were waiting on it, or about to start there, go back to queued, in their place in their user's queue, so another machine can take them. They don't end in an error. The server tries the machine again every 30 seconds.

Lines already running on the machine are left alone. The server checks on them when the machine is back.

The settings in force

maestro settings

Policies and the score

The queue described the three queues a line passes on its way to a machine. A policy picks who leaves each one. An administrator picks the policies, and maestro settings shows the ones in force.

The three policies

SettingThe choice it makesQueue
userWhich of one user's queued lines is that user's headUser queue
dispatcherWhich of a group's heads goes to a machine in the group's turnDispatcher queue
machineWhich of the lines waiting on a machine startsMachine queue

All three are fifo until an administrator changes them. Lines then go in the order they were queued, oldest run first, and on a machine the oldest waiting line holds back the others until it fits.

What a policy can be

The user and dispatcher policies choose before a line is on a machine. At that point there is no free space to fit the line into, so these policies only put lines in an order.

PolicyServes first
fifoThe oldest
lcfsThe newest
siroOne at random. The same seed gives the same choices.
pqThe one with the highest score. Among equal scores, the oldest.

The machine policy can be any of those four, and it also has four that look at the machine's free cores and memory.

PolicyServes first, among the lines that fit now
fifo-skipThe oldest
best-fitThe one that leaves the least free
weighted-best-fitAs best-fit, with the time a line has waited counting in its favour by ω3. A line that fits badly still starts eventually.
tetrisThe one whose cores and memory are most like what the machine has free, so that less of either is stranded (Grandl et al., 2014)

On a machine, fifo and lcfs are strict. They start their first choice if it fits, and start nothing while it doesn't. siro and pq choose among the lines that fit now, as the four policies in the second table do.

The score

pq gives every candidate line a score and serves the highest.

s = ω1·cores + ω2·memory + ω3·waiting + ω4·share

TermWhat it is
coresThe line's cpus, as a fraction of the cores all machines have for lines, summed
memoryThe line's memory, as a fraction of the memory all machines have for lines, summed
waitingThe time since the line's run was queued, divided by the horizon. The horizon is an hour unless horizon_minutes says otherwise.
shareThe user's share of the machines, as a fraction of every user's share added together

The cores and memory are fractions of all the machines together, so they are small when there are many machines. ω1 and ω2 then need to be larger to weigh as much as waiting and share do.

An administrator sets the four weights, and a weight can be negative.

WeightSettingEffect
ω1cpu_weightBelow 0, lines that ask for few cores go first.
ω2memory_weightBelow 0, lines that ask for little memory go first.
ω3aging_weightAbove 0, a line's score grows while it waits, so no line waits forever.
ω4share_weightBelow 0, a user who holds less of the machines goes first.

A worked example

Take a lab whose machines have 32 cores for lines in all, with dispatcher = pq and these weights: ω1 = −0.4, ω2 = 0, ω3 = 0.5 and ω4 = −1. The horizon is an hour. Two users of a group each have a head.

Bo's line has the higher score, so it goes to a machine first. Ada's line has waited longer and is smaller, but Ada already holds three times what Bo holds, and with these weights the share outweighs the rest.

Giving Bo's line a machine raises Bo's share, because an assigned line counts as held. The scheduler works the shares out again before the next turn.

A user's share

The share setting chooses how a user's share is measured.

MeasureA user's share is
drfThe dominant share now. Take the cores the user's lines hold as a fraction of the cores the machines have for lines, and the same for memory. The share is the larger of the two fractions (Ghodsi et al., 2011).
weighted-drfAs drf, with each fraction divided by the user's weight for that resource. An administrator sets the weights for each user, and a user without any has 1 for both.
assetThe two fractions added together. It is there for comparison only, because it lacks the sharing-incentive property that drf has.
decayThe dominant share of what the user's lines have used in the past. Usage counts half as much after each half-life, which is a week unless half_life_hours says otherwise. Slurm's fair-share works this way.

For drf, weighted-drf and asset, the lines a user holds are those that are assigned, starting or running.

Suppose the machines of the lab in the example have 32 cores and 96 GB for lines in total, and the measure is drf. Ada's lines hold 12 cores and 16 GB. That is 0.375 of the cores and 0.167 of the memory, so her dominant share is 0.375. Bo's lines hold 3 cores and 12 GB, which is 0.094 and 0.125, so his is 0.125. The score uses each as a fraction of the two together, which gives 0.75 for Ada and 0.25 for Bo.

With dispatcher = pq, share = drf and ω4 = −1, the queue is the classic fair queue of DRF, in which the user who holds the least goes next.

The network

orq is reached through the reverse proxy and nothing else. The compose file publishes its port 3005 on 127.0.0.1, so only the host itself reaches it.

A reverse proxy in a container of its own reaches the host through Podman's bridge, at host.containers.internal, and a port published on 127.0.0.1 may not answer there. Try it on your host. If the proxy can't reach orq, do one of two things:

  • Set ORQ_BIND in .env to an address of the host that the proxy reaches and other hosts don't.
  • Put the proxy and orq on one Podman network, have the proxy reach orq by its name, and remove the ports entry from the compose file.

The host also needs a firewall that lets in SSH and the ports the reverse proxy listens on, usually 80 and 443, and nothing else. A port that rootful Docker or Podman publishes can get past some firewalls' rules, so publish orq on 127.0.0.1 even behind one. With firewalld:

firewall-cmd --permanent --add-service=http --add-service=https
firewall-cmd --permanent --list-services   # remove any other with --remove-service
firewall-cmd --reload

Redis

Redis holds the sessions of the Maestro page, so whoever can write to it can make a session and sign in as anyone, administrators included. Builds run on the same host and may reach it. Hold it to two rules:

  • Give it a password. Make one with openssl rand -hex 32, which needs no escaping in a URL. Start Redis with --requirepass <password>, or put requirepass <password> in its redis.conf. Then set REDIS_URL=redis://:<password>@host:port/db in .env. Unless MODE=dev, orq logs a warning at start while REDIS_URL has no password.
  • Don't publish its port beyond the host. Other hosts must not reach it.

A Redis that other services share gets the same care from each of them. Any one of them that publishes it, or lets its own users reach it, opens Maestro's sessions too. When the Redis belongs to another compose project, its owner sets the password there, and you then set it in REDIS_URL.

Sessions and keys

Signing out of Maestro ends the Maestro session and leaves the user signed in at the provider. Signing out at the provider leaves an open Maestro session running until it expires.

The CLI doesn't use sessions. maestro login has the user approve a code on the page, and orq then gives the CLI a Maestro key of its own. orq stores only the key's hash. A key expires KEY_TTL after it was issued, 90 days by default.

A key can be revoked three ways. Its owner revokes it with maestro keys rm, maestro logout revokes the key it holds, and an administrator revokes every key of a user with Revoke keys in Admin › Groups. A revoked key stops working at once.

Whether a user is an administrator is read from their row in users on every request. That row is as fresh as their last sign-in on the page. A user removed at the identity provider keeps a working key for at most KEY_TTL, so revoke their keys when you remove them.

Adding machines

A machine is a host whose Podman runs users' containers. orq connects to it over SSH and talks to the Podman socket through that connection. The machine needs an SSH server and Podman's API socket, and no Maestro software.

Preparing a machine

Run this on the machine, as the user the containers will run as:

systemctl --user enable --now podman.socket
loginctl enable-linger "$USER"     # keep the socket up without a session
ls /run/user/$(id -u)/podman/podman.sock

Make an SSH key pair without a passphrase for orq, and add the public key to that user's ~/.ssh/authorized_keys.

Let the user run commands over SSH. orq reads how loaded a machine is with a small shell script that uses /proc, df and nvidia-smi. A user who may only reach the socket still runs lines, but maestro top then shows the machine's containers and nothing else.

Holding lines to their cores

Some machines can't limit how much CPU a container uses. This happens with rootless Podman when the user's systemd doesn't pass down the cpu cgroup controller, which is the default on Ubuntu 22.04. On such a machine lines still count their cpus toward the machine's capacity, but a line that uses more cores gets them and slows the others down.

To get the limit, delegate the controllers to users once:

sudo mkdir -p /etc/systemd/system/user@.service.d
printf '[Service]\nDelegate=cpu cpuset io memory pids\n' |
  sudo tee /etc/systemd/system/user@.service.d/delegate.conf
sudo systemctl daemon-reload

Then have the Podman user sign out of every session, or restart the machine, so that the user's systemd starts again with the new setting. podman info should now list cpu under cgroupControllers.

Adding it to Maestro

On the Maestro page, open Admin › Machines and fill in:

  • the host, the SSH port and the user
  • the socket path, such as /run/user/1000/podman/podman.sock
  • the private key
  • how many cores and how much memory to keep back for the machine's own system
  • the host key, or nothing (see below)

When you save, orq connects and asks Podman for its version and for the machine's cores and memory. It saves the machine only if that works, and it refuses a reserve that would leave nothing for lines. orq asks again every time it checks the machine, so it notices when a machine gains or loses cores or memory.

The host key

If you leave the host key empty, orq pins the key the machine presents on that first connection and shows its fingerprint. Compare the fingerprint with the output of ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the machine. You can instead paste the line that ssh-keyscan -t ed25519 <host> prints.

The secret that protects the keys

orq stores private keys encrypted with MACHINE_SECRET and never sends them back to the page. MACHINE_SECRET must be at least 32 characters, and openssl rand -base64 32 makes a good one. While it is empty, machines are turned off. If you change it, orq can no longer read the keys it stored.

What orq does on a machine

Copying images

The first time a line needs an image on a machine, orq copies it there by streaming podman save into podman load over SSH, gzipped. The image stays on the machine for the next run.

Starting containers

orq starts each container with the line's cores, memory and environment, and a limit on processes, which is RUN_PIDS and 512 by default.

It always uses Podman's file log driver (k8s-file), whatever the machine's default is. Under journald, the user Podman runs as may not be allowed to read the journal, and the logs would come back empty.

Collecting results

When a container ends, orq takes back its logs and outputs and then removes it.

Sweeping

orq sweeps each machine when it starts, every 10 minutes, and whenever an image is removed.

orq labels everything it creates with maestro.orq, set to a name it gave itself the first time it started. Its images also carry their build, and its containers carry their run and line. The sweep removes two things: a container of orq's own that no line has on that machine, and an image of orq's own that orq no longer has and no line needs there.

The sweep touches nothing else on the machine. The machine's own images and containers stay, and so do those of another orq that uses the same machine.

When a machine can't be reached

A machine orq can't reach gets no new lines. The lines waiting on it, or about to start there, go back to queued so another machine can take them. orq tries the machine again every 30 seconds. Lines already running on it are left alone.

orq doesn't keep SSH connections open. The runner, a check of the machine, and maestro top each open their own. maestro top opens one every couple of seconds while someone is watching.

Who sees what

Users see the list of machines and whether orq can reach each one (maestro machines), how loaded each is (maestro top), and the containers of their own runs. Administrators see every container. They also see the server orq runs on, listed as orq.

Machines behind a proxy

Some machines can't be reached over plain TCP, such as one behind Cloudflare Access. orq reaches those through a proxy command, the way ssh does with ProxyCommand. orq runs the command and speaks SSH over the command's standard input and output. The host key is still pinned, and everything else works as it does for any machine.

Turning proxy commands on

A proxy command runs a program inside orq's container, so allowing them lets any administrator run commands on the server. orq refuses proxy commands unless MACHINE_PROXY_COMMANDS=true. While the setting is off, a machine saved with a proxy command shows as unreachable and says why.

Cloudflare Access

In the machine's form, set the host to the Access hostname, such as q1-ssh.example.com, and set the proxy command to:

cloudflared access ssh --hostname %h

orq replaces %h, %p and %r with the host, the port and the user, and %% with a %. cloudflared is included in orq's image.

Under "Proxy environment", paste the Access service token:

TUNNEL_SERVICE_TOKEN_ID=…
TUNNEL_SERVICE_TOKEN_SECRET=…

You can also paste a file of export NAME=value lines as it is, such as one you source before running ssh.

orq stores the proxy environment encrypted with MACHINE_SECRET, as it does the private key, and never sends it back. The page shows only the names of the variables. Saving an edit with the field left empty keeps what is stored.

The command runs with PATH, HOME and the variables you pasted. It gets none of orq's own environment.

What a proxy costs

orq doesn't keep connections open. Each connection from the runner, from a check of the machine, or from maestro top starts its own cloudflared, which adds between half a second and a second. maestro top opens one every couple of seconds while someone is watching.

If cloudflared fails, the machine's error shows what it printed.

An administrator sets the scheduler up on the Maestro page, under Admin › Settings. Policies and the score explains what each policy and weight does.

A saved change applies from the scheduler's next pass, to lines that haven't moved yet. Lines already assigned stay where they are.

Checking what is in force

maestro settings prints the saved settings for any user, and maestro queue ends with a one-line summary of them.

Each line records the settings it was assigned under and the group its user was in. An export that spans a change of settings therefore still says which settings served which line.

Settings saved before orq had three queues had a select policy, which chose among a group's users. orq reads it as the dispatcher policy, so a pq there stays pq. Their allocate and staged_capacity no longer set anything.

If orq can't read the saved settings after an upgrade, it falls back to FIFO in every queue so that lines keep starting, and its log says why. Save the settings again to fix it.

Trying policies before choosing

Comparing policies offline runs the same scheduler over a recorded or generated workload, so you can compare two setups without waiting for the lab to live through them.

Groups

Every user is in one group, and groups take turns at the machines. Each group has a dispatcher queue of its own, made of its users' heads, so a group with many users can't crowd out a group with few.

A new Maestro has one group, the default group, and everyone is in it. New users start there. It stays the only group until an administrator makes more.

Managing groups

Admin › Groups on the Maestro page lists the groups and their members.

  • "New group" creates a group, and Rename changes a group's name.
  • "Add member" moves a user into a group. A user is in one group at a time, so this takes the user out of the group they were in.
  • The ✕ beside a member sends that user back to the default group.
  • Remove deletes a group and sends its users back to the default group. The default group itself can't be removed.

Under the groups, "Maestro keys" lists every user. "Revoke keys" revokes all of a user's Maestro keys after it asks.

Moving a user affects the lines assigned from then on. Their queued lines wait in the new group's dispatcher queue. Lines already assigned keep the group they were assigned in.

How groups affect the queue

Inside a group, the dispatcher policy chooses whose head goes to a machine next. Between groups no policy chooses. The groups take turns, one line a turn. The queue describes a turn.

maestro queue shows each user their group: how many of its lines are queued, how many of those are heads in its dispatcher queue, and how many are assigned.

Each line records the group its user was in when the line was assigned. maestro export writes it, so moving a user later doesn't change what the export says about earlier lines.

Comparing policies offline

sim is a program in the maestro-orq repository. It runs orq's own scheduler over a workload on a simulated clock, so you can compare policies without using the machines. It also measures how lines were served, whether they came from a simulation or from a real Maestro.

cd maestro-orq
go run ./cmd/sim generate -users 4 -groups 2 -hours 8 > workload.csv
go run ./cmd/sim run -machines Q1:32:65536:2:4096 -config drf.json < workload.csv > lines.csv
go run ./cmd/sim evaluate -cpus 30 -memory 61440 -lambda-j 1h -lambda-o 1h < lines.csv

A workload

sim generate writes a workload: runs of lines that users submit over a number of hours. The group column puts each user in a group. A workload without that column has every user in group 1.

The machines

-machines takes a list separated by commas. Each machine is written name:cpus:memory[:reserve_cpus:reserve_memory][@speed], with memory in MB.

ExampleMeaning
Q1:32:65536:2:409632 cores and 64 GB, with 2 cores and 4 GB kept back
Q2:8:16384@1.58 cores and 16 GB. Lines run 1.5 times as fast on it.

With @speed, how long a line runs depends on the machine it lands on.

The scheduler's settings

-config names a JSON file with the scheduler's settings, in the form GET /api/settings returns them under scheduler. This one is DRF:

{"dispatcher": "pq", "share_weight": -1}

Without -config, every queue is FIFO. The names are the settings of Policies and the score:

KindNames
Policiesuser, dispatcher, machine
Scorecpu_weight, memory_weight, aging_weight, share_weight, horizon_minutes

The machine queue and the drawdepth, seed

A file from before the three queues still works. Its select is read as dispatcher, and its allocate and staged_capacity are ignored.

A simulated line starts the moment it is chosen. A real line first waits for its image to be copied and its container to be created, which the simulation leaves out.

Measuring

sim evaluate reads lines from sim run or from maestro export and reports:

  • the mean wait, and how much of it was spent queued and assigned
  • the mean time in the system
  • the mean bounded slowdown
  • the utilization of cores and of memory
  • Jain's index of the users' slowdowns
  • the objective Z = F + λ_J·Φ_J + λ_O·Φ_O

An export from before the three queues has a staged column, which sim evaluate skips. Its lines' time queued then runs to when they were assigned.

The objective has three parts.

PartWhat it is
FThe mean time from a run's submission to the end of its last line
Φ_JThe gap between the largest and the smallest dominant share, among users who have unfinished lines, averaged over time
Φ_OThe fraction of the machines that is idle while some line waits, averaged over time

-lambda-j and -lambda-o say how much time one whole unit of Φ_J and of Φ_O is worth.

The Usage page on the Maestro page measures a real period the same way, under "Lines over a period". It uses what the machines have for lines at the moment you ask.

What orq keeps, and for how long

orq keeps four kinds of data: its record of builds and runs in SQLite, the files runs leave, the images, and short-lived answers in Redis.

The record, in SQLite

orq keeps everything about builds, runs and lines in its database, which lets it restart in the middle of a run. When it comes back:

  • it starts again the lines it was about to start
  • it picks up the containers it had started, where they are
  • it collects the containers that finished while it was down, as if it had been running

A build that orq was making when it stopped is marked failed, so it doesn't count against the user's image limit. orq removes any image that build left behind.

Backing up the database

The database is MAESTRO_ORQ_DB, which the compose file puts at /data/maestro-orq.db in the maestro-orq-data volume. orq opens it in WAL mode, so the latest writes sit in maestro-orq.db-wal beside it until SQLite moves them into the database. A copy of maestro-orq.db alone can miss them. Back the database up in one of two ways:

  • While orq runs, use SQLite's own backup, which reads both files consistently: sqlite3 maestro-orq.db ".backup maestro-orq-backup.db".
  • Stop orq, then copy maestro-orq.db together with maestro-orq.db-wal and maestro-orq.db-shm, if they are there.

Files, in /maestro/data

orq keeps the logs and outputs of runs under DATA_DIR, which is /maestro/data by default, as <user>/<run>/<line>/<file>. Each line keeps at most RUN_OUTPUT_MAX_MB of logs and outputs, 1024 by default.

The files stay until someone deletes the run. orq deletes none of them on its own, so size the volume for that, and ask users to remove the runs they no longer need with maestro runs rm.

USER_DATA_MAX_GB limits what all of a user's runs keep, and is off by default. orq adds up the user's files when they start a run. Once they keep that much or more, it refuses the run with "your runs keep 52 GB of the 50 GB allowed; delete one with maestro runs rm <run>". orq checks only when a run starts, so a run already started can take the user past the limit, by at most RUN_OUTPUT_MAX_MB for each of its lines.

Images

Each user keeps at most 10 built images. Admin › Settings changes the number. A build that would exceed it removes the image the user ran least recently, skipping any image a run is still using. The image goes from orq's Podman and from the machines. The record of its build, the runs of that build and their files are all kept.

Short-lived answers, in Redis

Lists are requested often, mostly by tab completion, so orq answers the slow ones from Redis. Redis holds no record that exists nowhere else. If you empty it, orq reads each answer again the next time it is asked.

Sessions of the Maestro page are in Redis too, so emptying it signs everyone out of the page. The CLI stays signed in, because its keys are in the database.

AnswerKept forDropped sooner when
A user's images (maestro builds, completing maestro run)60 sA build of theirs ends, or one of their images is removed
Runs (maestro runs, completing a run, the page)2 sTheir owner or an administrator starts, cancels or deletes one
A machine's status10 min. An answer older than 30 s, or 10 s if the machine was unreachable, triggers a new check in the background.The machine is edited
A machine's load (maestro top)2 s

In practice, what a user does shows at once, and what the runner does to a run, such as a line starting or ending, shows within 2 seconds. An image removed from Podman by hand, without orq knowing, can stay listed for up to a minute.

The list of builds is one fast query and isn't cached. The CLI caches nothing either, so each tab completion costs one request to orq.

On the machines

orq removes a container once it has the container's logs and outputs.

An image stays on a machine, so the next run of its build starts without a copy. It goes when orq removes the image itself, either to make room for a newer build or because of maestro builds rm. orq's sweep then removes it from every machine where no line needs it. Adding machines describes the sweep.

When something goes wrong

Signing in

"no Maestro server is set"

The CLI has no built-in server. In a terminal it asks for the address the first time. Where it can't ask, as in a script, name the server one of three ways: run maestro login --server https://maestro.example.org once, pass --server, or set MAESTRO_ORQ_URL.

A message that says to "sign in there"

--server or MAESTRO_ORQ_URL points the command at a server other than the one that issued your key. Run the maestro login --server command the message gives. It forgets the key you had for the other server.

"this Maestro key expired; run maestro login"

A Maestro key works for 90 days after it was issued, unless your administrator set another length (KEY_TTL). Run maestro login for a new key. maestro keys shows when each of your keys expires.

The keyring asks for a password every time, or there is no keyring

Sign in with maestro login --store-in-file, which keeps the key in the CLI's config file.

Building

The repository isn't found, or can't be cloned

Check that maestro repos lists it. If it doesn't:

  • On GitHub, the token must be a classic one with the repo scope.
  • GitHub and GitLab tokens expire after 30 days by default. maestro forges add with the same name replaces an expired one.
  • A self-hosted forge must be in the server's ALLOWED_FORGE_HOSTS, which an administrator sets.

The build fails

The last lines of the build log say why. The usual causes are:

  • a step of the Dockerfile fails
  • maestro.toml is invalid, or has a key Maestro doesn't know, which includes a misspelt one
  • the generator raised an exception, yielded nothing, yielded something that isn't a string, or brought the run to more than 1000 lines
  • the generator set a Config attribute other than outputs, cpus, memory and env
  • the generator imports a package outside Python's standard library, such as numpy

On the last cause: the package may well be installed in your image, but the generator runs inside the server, where only the standard library exists. See Where and when the script runs.

The Dockerfile can't find a file

The build's context is the root of the repository, even when maestro.toml says dockerfile = "docker/Dockerfile". Paths in COPY start at the root.

A step that runs git fails

Maestro's clone has no .git directory, so that the forge token doesn't end up in the image. A step such as RUN git rev-parse HEAD can't work.

The build is refused because of the image limit

you have 10 of the 10 images allowed (counting builds still running), and runs are using the rest; remove one with `maestro builds rm <build>`

A build normally makes room by removing the image you ran least recently. It can't when runs are still using every image you have. Wait for a run to end, or cancel one, and build again.

Running

The run is refused because a line is too large

line 3 asks for 64 cpus and 512 MB, which no machine it may use has for lines even with nothing else on it (see `maestro machines list`)

The line asks for more cpus or memory than any machine it may use has for lines. Ask for less, or allow more machines in machines. maestro machines shows what each machine has.

"the image of build 12 was removed; build it again"

You keep a limited number of images, and this one went to make room for a newer build, or you removed it with maestro builds rm. Build the commit again.

Lines wait for a long time

See Why a line is waiting.

A line ends failed

Its program exited with a code other than 0. maestro runs logs <run> <line> shows what it printed. Exit code 137 usually means the kernel killed it for using more memory than its memory.

A line ends error

The line couldn't start on its machine, or it lost its container when the machine restarted. The cause is on the server's side, and the line's status on the Maestro page says what happened. Run it again, and tell your administrator if it keeps happening.

The program is slow, or slows down other people's lines

It probably starts one thread for each core of the machine, when it should start one for each core it was given. Size it from MAESTRO_CPUS, as How many threads to start describes.

Results

An output is listed as missing

The program didn't write the file where maestro.toml says. A relative path in outputs starts at the image's WORKDIR, or at / when the image has none.

Logs stay empty until the line ends, or arrive in bursts

The program buffers what it prints. In Python, start it with -u, set PYTHONUNBUFFERED=1 in the image, or print with flush=True.

Logs or outputs stop early, with a note that they were cut

A line keeps at most 1 GB of logs and outputs, unless the administrator changed RUN_OUTPUT_MAX_MB.

Machines, for administrators

A machine shows as unreachable

The machine's error says why. The usual reasons are:

  • SSH refused the connection.
  • The host key changed.
  • The Podman socket isn't there. Run systemctl --user enable --now podman.socket on the machine, and loginctl enable-linger so that the socket stays up.
  • The machine uses a proxy command while MACHINE_PROXY_COMMANDS is off.

Lines waiting on the machine go to other machines, and orq tries it again every 30 seconds.

A machine runs lines but maestro top shows no numbers for it

The machine's SSH user can reach the Podman socket and can't run commands. The machine says so in maestro top. Preparing a machine explains what orq runs there.

Lines use more cores than they asked for

The machine's Podman can't limit CPU. See Holding lines to their cores.

Old runs have empty logs

orq creates containers with Podman's file log driver, whatever the machine's default is. Runs made by an orq from before that change, on a machine whose default is journald, may have empty logs.

starting, runningIn a container on the machine

It then ends in one of four ways.

StatusWhat happened
succeededThe program exited with 0.
failedThe program exited with another code.

The scheduler's words

WordMeaning
User queueA user's queued lines, in the order the user policy gives them
HeadThe first line of a user's queue, the one their group's dispatcher queue holds for them
Dispatcher queueThe heads of a group's users. In the group's turn, the dispatcher policy gives one of them a machine.
Machine queueThe lines assigned to a machine that wait for room on it, at most depth of them
PolicyThe rule that picks who leaves one of the three queues, such as fifo or pq
ScoreThe number pq ranks lines by, built from a line's cores, memory and waiting time and its user's share
ShareHow much of the machines a user holds or has used, as the chosen measure counts it

The queue describes the queues, and Policies and the score the policies, the score and the share.

Contributing

Each part of Maestro lives in its own repository and is developed and versioned on its own. The maestro repository holds them as git submodules.

RepositoryWhat it holds
maestro-orqThe server, in Go with Gin and SQLite
maestro-cliThe maestro command and this book, in Go with cobra and Bubble Tea, and mdBook
maestro-viewThe Maestro page, in Vue
maestro-templateThe repository users fork to start
maestroThe compose files that run the parts together

CONVENTIONS.md, at the root of the maestro repository, says where code goes in each part. Read it before you add a file. Deploying Maestro describes the development stack.

This book

The book is in maestro-cli/book and is written with mdBook. Every maestro binary carries a built copy, which maestro docs opens offline.

cd maestro-cli
sh book/build.sh                 # build it, for the next go build to embed
mdbook serve book                # or edit it with a live preview, on :3000

book/build.sh does three things:

  1. It writes Every command from the CLI itself, with maestro gen-docs.
  2. It builds the book.
  3. It packs the result where go build embeds it.

The script uses mdbook and mdbook-mermaid when they are installed. Otherwise it downloads the versions it names into your cache. goreleaser runs it before every release.

When you move or rename a page

cmd/docs.go holds the topics of maestro docs, each with the page it opens. A page that moves in the book has to move there too. go test ./cmd fails while a topic points at a page that SUMMARY.md doesn't list.
